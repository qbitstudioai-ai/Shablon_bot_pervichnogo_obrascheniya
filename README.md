# Шаблон бота первичного обращения

## Статус документа

Этот файл фиксирует согласованную концепцию продукта до начала проектирования конкретных нод, таблиц и кода.

Это не техническая спецификация готового решения. Детали будут уточняться по мере разработки, но основные принципы ниже считаются исходной архитектурой шаблона.

## Цель продукта

Создать качественного бота первичного обращения, которого можно быстро внедрять в разные компании.

Новое внедрение должно выполняться не разработкой продукта заново, а развёртыванием экземпляра из эталонного шаблона:

1. скопировать готовый workflow;
2. изменить несколько заранее обозначенных параметров;
3. подключить Credentials;
4. указать схему и места хранения данных в Supabase;
5. протестировать;
6. запустить рабочую версию для новой компании.

Главный критерий:

> Если для внедрения в новую компанию приходится переписывать основную логику бота, значит шаблон спроектирован неправильно.

## Основные решения

### 1. Один продукт — один эталонный workflow

Для бота первичного обращения создаётся один эталонный workflow:

```text
TEMPLATE — Бот первичного обращения
```

Для каждой компании создаётся отдельная копия:

```text
Компания 1 — Бот первичного обращения
Компания 2 — Бот первичного обращения
Компания 3 — Бот первичного обращения
```

Каждая рабочая копия изолирована от других компаний. Название компании присутствует в названии workflow, но общей логике не требуется программно определять, для какой компании она работает.

### 2. Каналы — не отдельные продукты

Telegram, сайт, Авито и будущие источники — это каналы одного продукта, а не отдельные боты.

Не создаются независимые продукты:

```text
Бот в Telegram
Бот на сайте
Бот на Авито
```

Вместо этого один workflow принимает обращения из подключённых каналов, приводит их к единому формату и после обработки возвращает ответ в исходный канал.

Обязательное правило:

> Ответ всегда отправляется в тот канал и тот диалог, из которого пришло обращение.

### 3. Поведение бота настраивается в n8n

Все параметры, влияющие на поведение workflow, находятся в n8n.

Supabase не используется как панель управления логикой бота и не хранит конфигурацию, определяющую его поведение.

### 4. Supabase хранит данные и знания

Supabase используется для:

- хранения обращений, диалогов и результатов обработки;
- хранения данных, необходимых для отчётов и будущего дашборда;
- хранения базы знаний;
- хранения документов, фрагментов и векторов для RAG;
- хранения минимальных технических логов.

Для каждой компании создаётся отдельная schema:

```text
company_001
company_002
company_003
```

Структура schema у всех компаний должна быть одинаковой. В будущем она должна создаваться единым SQL-шаблоном, без ручного создания таблиц.

Точный состав и названия таблиц будут определены отдельно после разбора реального рабочего процесса.

## Общая архитектура workflow

```text
КАНАЛЫ ВХОДА
Telegram / Сайт / Авито / другие
        ↓
НОРМАЛИЗАЦИЯ
единый внутренний формат сообщения
        ↓
CORE — НЕ ТРОГАТЬ
анонимизация
контекст и история
получение знаний из Supabase
RAG
передача в LLM
проверка и обработка ответа
классификация
бизнес-логика
        ↓
ИНТЕГРАЦИИ
CRM / уведомления / другие системы
        ↓
МАРШРУТИЗАЦИЯ ОТВЕТА
определение исходного канала
        ↓
ОТВЕТ В ИСХОДНЫЙ КАНАЛ
        ↓
SUPABASE
сохранение данных, результата и статуса
```

Фактический порядок отдельных операций может измениться после разбора рабочего процесса. Неизменным остаётся разделение на входные адаптеры, нормализацию, CORE, интеграции и выходные адаптеры.

## Нормализация входящих сообщений

Каждый канал передаёт данные в своём формате.

Например, Telegram может передавать:

```text
chat_id
username
text
```

Авито может передавать:

```text
conversation_id
user_id
message
```

После входного блока данные должны преобразовываться в единый внутренний формат. Предварительно он может включать:

```text
request_id
source
conversation_id
user_id
message
received_at
attachments
```

После нормализации CORE не должен зависеть от особенностей Telegram, сайта или Авито.

На выходе значение `source` направляет ответ в соответствующий адаптер:

```text
telegram → отправить в Telegram
avito    → отправить в Авито
website  → отправить на сайт
```

Окончательный внутренний формат будет утверждён при проектировании workflow.

## Разделение workflow на визуальные блоки

В n8n необходимо визуально отделить изменяемую часть от ядра продукта.

### МЕНЯТЬ ПРИ ВНЕДРЕНИИ

Этот блок выделяется одним цветом и содержит только параметры, которые проверяются или изменяются при создании экземпляра для новой компании:

- основной prompt и дополнительные prompts;
- подключённые каналы;
- Credentials каналов;
- схема и места хранения данных в Supabase;
- источник базы знаний и векторное хранилище;
- тип CRM;
- Credentials CRM;
- модель LLM, если она действительно должна отличаться;
- необходимые бизнес-параметры конкретной компании;
- адреса технических webhook и других интеграций.

Количество таких параметров должно оставаться минимальным. Новый параметр добавляется только тогда, когда есть реальная потребность внедрения.

### CORE — НЕ ТРОГАТЬ

Этот блок выделяется другим цветом и содержит общую логику продукта:

- приведение входных данных к единому формату;
- формирование уникального идентификатора запроса;
- анонимизация;
- получение истории и контекста;
- работа с базой знаний и RAG;
- обращение к LLM;
- проверка и разбор ответа LLM;
- классификация обращения;
- основная бизнес-логика;
- защита от повторной обработки;
- обработка ошибок и безопасные повторные попытки;
- техническое логирование;
- подготовка результата для выходных адаптеров.

При обычном внедрении этот блок не редактируется.

### АДАПТЕРЫ

Отдельные визуальные блоки отвечают за внешние системы:

- Telegram;
- сайт;
- Авито;
- Bitrix24;
- amoCRM;
- будущие каналы и интеграции.

Особенности внешнего API должны оставаться внутри соответствующего адаптера и не проникать в CORE.

## CRM и другие интеграции

Не следует одновременно запускать все CRM-ноды в расчёте на то, что ненужные ничего не передадут.

Выбор выполняется явно:

```text
CRM_TYPE = bitrix
        ↓
      Switch
     ↙      ↘
Bitrix24   amoCRM
```

Для другой компании значение может быть:

```text
CRM_TYPE = amo
```

Такой подход:

- исключает лишние запросы;
- уменьшает вероятность ошибочной передачи данных;
- делает выбранную интеграцию понятной;
- облегчает тестирование.

Тот же принцип применяется к другим взаимоисключающимся интеграциям.

## Credentials и секреты

Токены, API-ключи, пароли и другие секреты не записываются:

- в обычные ноды с открытым текстом;
- в prompt;
- в таблицы конфигурации Supabase;
- в экспортируемый JSON workflow;
- в Git-репозиторий.

Для секретов используются n8n Credentials или переменные окружения, если это потребуется архитектурой.

Пример единого именования:

```text
COMPANY01_TELEGRAM
COMPANY01_AVITO
COMPANY01_SUPABASE
COMPANY01_BITRIX24
COMPANY01_AMOCRM
```

Точный стандарт именования будет утверждён перед первым внедрением и затем применяться ко всем компаниям.

## Защита от дублей

Одно обращение не должно:

- дважды обрабатываться LLM;
- дважды сохраняться как новое обращение;
- дважды создавать сущность в CRM;
- дважды отправлять ответ пользователю.

Для каждого входящего события нужен уникальный `request_id` или другой ключ идемпотентности.

При повторном запуске workflow система должна понимать, какие операции уже успешно выполнены, и не повторять действия с внешними последствиями.

Конкретный механизм будет выбран после изучения форматов идентификаторов Telegram, сайта и Авито.

## Ошибки и повторный запуск

Необходимо отдельно обработать сбои:

- LLM;
- Supabase;
- CRM;
- базы знаний;
- входного канала;
- отправки ответа в исходный канал.

Минимальная техническая информация о выполнении:

```text
workflow
source
request_id
status
error
created_at
```

Повторные попытки допускаются только там, где они не создают дубли. Ошибка одной внешней интеграции не должна незаметно терять обращение клиента.

Точная стратегия повторов, ожиданий и уведомлений будет спроектирована после разбора рабочего процесса.

## Версии шаблона

Должен существовать один эталонный TEMPLATE, из которого создаются production-копии.

Для каждого экземпляра необходимо понимать:

- из какой версии шаблона он создан;
- какие индивидуальные изменения в нём сделаны;
- какие исправления CORE уже перенесены;
- какие исправления ещё требуется перенести.

Правило версий нужно определить до появления нескольких production-копий. Механизм обновления работающих экземпляров пока не выбран и является отдельной задачей проектирования.

## Процесс внедрения в новую компанию

Целевой процесс:

1. Скопировать эталонный workflow.
2. Переименовать копию по единому правилу.
3. Проверить блок «МЕНЯТЬ ПРИ ВНЕДРЕНИИ».
4. Настроить prompts и необходимые бизнес-параметры.
5. Подключить нужные входные и выходные каналы.
6. Подключить n8n Credentials.
7. Выбрать CRM через явный маршрутизатор.
8. Создать schema компании в Supabase по единому SQL-шаблону.
9. Указать schema, таблицы и базу знаний в соответствующих нодах.
10. Проверить ответ в тот же канал и диалог.
11. Проверить обработку ошибок и защиту от дублей.
12. Провести тестирование.
13. Активировать production-workflow.

Цель — проходить этот процесс без изменения CORE.

## Критерии готовности шаблона

Шаблон можно считать тиражируемым, если:

- новый экземпляр создаётся копированием одного workflow;
- все изменяемые места собраны и визуально обозначены;
- CORE не редактируется при стандартном внедрении;
- несколько каналов используют одну общую логику;
- ответ возвращается в исходный канал и диалог;
- CRM выбирается явно через маршрутизацию;
- данные компаний изолированы разными schema;
- структура schema одинакова;
- секреты хранятся безопасно;
- повторная обработка не создаёт дубли;
- ошибки не приводят к незаметной потере обращения;
- известна версия TEMPLATE, на которой основан экземпляр.

## Что пока не зафиксировано

Следующие вопросы намеренно оставлены открытыми:

- реальный порядок нод внутри workflow;
- точный состав блока «МЕНЯТЬ ПРИ ВНЕДРЕНИИ»;
- окончательный формат нормализованного сообщения;
- точная структура таблиц Supabase;
- SQL-шаблон создания schema компании;
- структура базы знаний и RAG;
- правила prompts;
- метрики и отчёты для руководителя;
- архитектура дашборда;
- механизм переноса обновлений CORE в работающие копии;
- стратегия обработки ошибок и повторов;
- тестовый контур и критерии приёмки конкретного внедрения.

Эти решения должны приниматься после разбора фактического рабочего процесса, чтобы архитектура основывалась на реальных потребностях, а не на предположениях.

## Следующий этап

Перед созданием технической архитектуры необходимо разобрать, как сейчас выполняется работа:

- откуда приходит обращение;
- какие данные доступны на входе;
- что бот должен определить и сделать;
- когда нужен человек;
- что и куда передаётся;
- какие результаты сохраняются;
- какие отчёты действительно нужны.

После этого можно спроектировать фундамент: workflow n8n, структуру Supabase, правила интеграций и тестирование.
