# TPL-FIN — Последний этап функциональной разработки шаблона

Обновлено: 2026-10-18. Решение Павла от 18.10.2026.

## Цель и граница остановки

Довести проверенный TEST-бот qBit до повторно используемой основы, закончить четыре задачи в установленном порядке и **остановить добавление новых возможностей шаблона**. Дальше — отдельные внедрения компаний и исправление подтверждённых дефектов, а не бесконечная доработка продаж.

Функциональная остановка НЕ равна разрешению промышленного запуска и НЕ закрывает автоматически полные `QA-01` / `REL-01`: обязательные проверки из `docs/RELEASE_CHECKLIST.md` сохраняются. Дашборд, CRM и новые внешние каналы не включены в эти четыре задачи и остаются отдельным объёмом, если обещаны заказчику. Нельзя объявлять полный изначальный продукт завершённым при отсутствии этих компонентов.

Исходная ветка на момент фиксации: `main`, commit `71db6352e8011503eeeeacc5242fc8e1f9ac940d`. Эта фиксация — документация; импорт workflow, миграции, выпуск и серверные операции ею не выполняются.

## Проверенное и непроверенное на дату фиксации

- В TEST подтверждены ответы Telegram с active-only RAG, служебные темы, частное уведомление менеджера, atomic Take и ручные ответы, отмена прежнего ожидания новым вводом, а 18.10.2026 — два LLM-догоняющих через 1 и 3 минуты на тестовом аккаунте без запрета инициативы.
- TEST SQL `DB-03I` применён по сообщённому результату `VERIFIED`; новый TEST Sales Brain v1.3 отвечает и отправляет два догоняющих. Однако ни DB-03I, ни очищенный экспорт v1.3 не зафиксированы в `workflows/current/` и `sql/` GitHub как проверенная переносимая основа.
- Правила тематической блокировки и DB-функция фиксации нарушений предусмотрены; прохождение всей цепочки 1→2→3→блокировка→разблокировка на актуальном runtime ещё не подтверждено.
- Сценарии отказа канала и восстановления, полная система ошибочных уведомлений, второй tenant и клиентский сайт qBit в рамках этой версии не подтверждены.

## Порядок и критерии

### TPL-FIN-00 — фиксация плана — DONE / documentation only

Критерий: этот план, README, PROJECT_STATE, SESSION_HANDOFF и связь с прежним E2E-планом читаются из одного commit `main`. Никаких изменений SQL, JSON или сервера.

### TPL-FIN-01 — тематика, попытки обойти правила, блокировка — NEXT

Зависимость: актуальная тестовая копия клиентского workflow и действующий DB guard/violation API. Начинать с аудита фактической логики в n8n, а не переписывать существующее без проверки.

- Темы, бизнес-описание, допустимый smalltalk, исключения и порог нарушений задаются доверенным блоком настроек компании; для оконной компании окно/остекление является основной темой без правки CORE, автоматизация qBit не остаётся скрытой константой.
- Семантическая проверка различает продажные возражения, smalltalk, неоднозначность, подтверждённые посторонние темы, injection и запрос менеджера. Не строить её на одном списке слов. «Дорого», «я подумаю», «не подходит» — **возражения продавцу**, не блокировка и не моментальное закрытие сделки.
- Для qBit проверить три отдельных подтверждённых нарушения → предупреждения 1, 2, 3 и логическая блокировка; после неё вход сохраняется, но бот не отвечает. При обычном приветствии, неоднозначности, недостатке знаний и технической ошибке счётчик не растёт. Отдельно проверить попытку получить промт/секреты и ручную административную разблокировку.
- Логическая блокировка Telegram означает остановку автоматических ответов, а не невозможный запрет пользователю писать в личный чат. Проверить отсутствие влияния на другие аккаунты/компании.

Критерий готовности: демонстрация в TEST всех положительных и отрицательных случаев с доказательствами состояния БД и сообщений; настройка тематики qBit→оконная компания меняется только через конфигурацию. Зафиксированы обновлённые спецификации и версия workflow.

### TPL-FIN-02 — критические ошибки и Telegram-оповещения разработчику — PENDING

Зависимость: TPL-FIN-01.

- Сделать общий технический обработчик ошибок n8n для обоих основных workflow (при необходимости отдельный Error Workflow без нового конкурирующего Telegram webhook). Уведомление в **доверенный приватный Telegram разработчика**, заданный настройкой/Credentials, не жестко зашитым реальным ID.
- Сообщение: компания/среда, workflow, **точное имя упавшей ноды**, короткий безопасный тип/текст ошибки, время, execution ID и ссылка на выполнение при наличии, критичность, результат повтора/нужное действие. Если ноду определить невозможно, писать «источник неизвестен», не придумывать.
- Критические пути: вход/подтверждение webhook, запись в БД, очередь/lease, guard, OpenAI и RAG, сохранение/Telegram отправка и подтверждение, проверка догоняющих, запрос/Take менеджера, загрузка/публикация знаний; позднее — web adapter. Ошибка модели или Telegram не должна выглядеть как успешная обработка.
- Фильтровать секреты, персональные данные, сырой текст сообщений и полные payload; не создавать рекурсивные уведомления и шквал одинаковых сообщений. Остановка всего n8n/БД требует **внешней** проверки, поскольку Error Workflow в упавшем n8n не запустится.
- Не делать слепые повторы при неизвестном результате Telegram/API; сценарии `WF-02B3C-E2E-03C` входят в эту проверку.

Критерий готовности: искусственно вызваны ошибки нескольких критических нод каждого workflow, корректные уведомления реально доставлены, показаны подавление дублей, безопасные логи и аварийный внешний сигнал при остановке n8n.

### TPL-FIN-03 — эталонные безопасные workflow/SQL и переносимость — PENDING

Зависимость: TPL-FIN-01 и TPL-FIN-02, результаты их TEST проверок.

- Снять **свежие** экспорты реально работающих клиентского и служебно-документного workflow, сверить с текущими файлами в `workflows/current/`. За основу Sales Brain брать последний фактически проверенный TEST v1.3 плюс прошедшие последующие исправления, не устаревшую копию GitHub.
- Внести совместимые изменения для разделения компаний: убрать жёстко заданные обращения к qBit TEST schema/ролям/ссылкам из переносимого CORE; имена schema и роли назначает **доверенная конфигурация/ограниченные Credentials**, не текст клиента и не ответ LLM. При необходимости подготовить полные SQL-файлы установки новых schema/ролей и проверок без прав на чужие schema.
- В репозитории сохранить оба полных repository-safe JSON, недостающие нормативные SQL (включая `DB-03I`, если признан частью релиза), версии и краткую инструкцию импорта/отката; удалить Credential refs, реальные Telegram/chat/webhook IDs, instanceId, токены, закреплённые данные, переписки и секреты.
- Импортировать тестовую копию для другой условной компании и проверить изоляцию доступа, RAG только из активных знаний своей компании, маршрутизацию и сохранённую функциональность qBit. Не переключать рабочий webhook без разрешения.
- Завершить незакрытые проверки E2E-03B/E2E-04, включая opt-out, ожидающего менеджера, подтверждённый перенос контакта, прерывания/отмены и регрессию после смены конфигурации. Убедиться, что до выпуска тестовые интервалы 1/3 минуты возвращены к утверждённым для компании.

Критерий готовности: конкретный Git commit с безопасными версиями двух JSON и SQL, прочитанный обратно с GitHub; тестовый импорт на отдельной компании и отрицательные проверки межкомпанейского доступа; доказан путь отката. Наличие файла без runtime-проверки не считать готовностью.

### TPL-FIN-04 — сайт qBit как второй клиентский канал — LAST

Зависимость: TPL-FIN-03. Сначала тестовый сайт и тестовый workflow; рабочий сайт и трафик — только по отдельному разрешению Павла.

- Подключить сайт qBit к **тому же продающему CORE** и знаниям qBit, что Telegram, через отдельный проверенный web adapter. Telegram продолжает работать, новые Telegram webhook не создаются.
- Веб-канал сохраняет входящее событие, защищает сессию/источник, правильно связывает ответы с посетителем и не смешивает чужие разговоры; память, guard, RAG, продажи и handoff повторно используются.
- Догоняющие в web-канале учитывать только при реальной возможности доставки и согласованном праве на контакт. Закрытая вкладка не равна доставленному сообщению; Telegram ID и web-сессии не объединяются по имени/догадке.
- Проверить на тестовом сайте одновременную работу двух каналов, безопасность входа, деградацию/перезапуск, логирование ошибок и запрет инициативы. Зафиксировать согласованную обработку персональных данных и ограничения внешних LLM.
- После успешного теста подготовить выпуск и откат сайта qBit. Сохранить итоговый безопасный Git snapshot с web adapter, схемой подключений и тестами. Сам факт добавления кода не разрешает включить рабочий сайт.

Критерий готовности: TEST сайт ↔ qBit CORE работает наряду с Telegram, переходы и ограничения проверены; после отдельного разрешения рабочий сайт проверен либо явно отмечен как «готово к переключению, но не включено». Финальный Git snapshot прочитан обратно.

## Условие остановки

Когда TPL-FIN-01…04 действительно подтверждены, фиксируем завершение **функционального шаблона Telegram + сайт qBit** и больше не добавляем функции без нового решения Павла. Невыполненные обязательные `QA-01`/`REL-01`/`RELEASE_CHECKLIST` не закрываем формально: промышленный запуск каждой новой компании требует своей приёмки, изоляции, резервирования, мониторинга и явного разрешения на трафик. Отдельные дашборд/CRM/другие каналы остаются только как возможный самостоятельный проект, не задерживают эту функциональную остановку, но не считаются реализованными.

Первое действие следующей сессии: `TPL-FIN-01` — аудит и E2E тест тематической блокировки актуального TEST бота. Не начинать одновременно TPL-FIN-02…04.
