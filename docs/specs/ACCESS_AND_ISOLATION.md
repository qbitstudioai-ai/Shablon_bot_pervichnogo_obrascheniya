# Доступ и изоляция в одном серверном Supabase

## Зафиксированное решение

Supabase один, на сервере Павла; PostgreSQL и pgvector общие. Компании разделены по schema, а не по облачным проектам. Studio — административный интерфейс, доступный только Павлу и доверенному обслуживанию.

Базовый путь доступа выбран однозначно:

- n8n обращается к PostgreSQL через Postgres-ноды с ограниченными ролями своей компании;
- серверная часть отдельного дашборда использует собственные ограниченные подключения;
- браузер обращается к серверному API своего дашборда, не к таблицам компаний напрямую;
- пользовательские schema не публикуются в Supabase Data API;
- общий service_role, postgres и ключи администратора не используются в обычных клиентских/служебных workflow или сервере дашборда.

Это реализуемо в одной установке. Нет требования создавать Supabase-проекты для компаний. Наличие schema — логическое разделение; защиту дают реальные права и проверка авторизации.

## Матрица прав

Для каждой компании и среды создаются отдельные роли. Роли приложений не владеют таблицами, не имеют BYPASSRLS, прав создания schema, смены привилегированных ролей и доступа к другим компаниям.

| Роль | Разрешено внутри своей компании | Запрещено |
|---|---|---|
| Клиентский workflow | Регистрация сообщений/заявок; состояние, очередь, рабочая память; чтение активных знаний через функцию; запись технических событий | Оригиналы и черновики знаний; публикация знаний; чужие schema |
| Служебный workflow | Приём документов, оригиналы, версии, проверочный поиск, публикация; технические уведомления | Чужие schema; чтение сырых переписок; изменение логики продаж |
| Сервер дашборда: чтение | Подготовленные показатели, разрешённые диалоги, состояние знаний/интеграций | Изменение переписки, очереди и знаний; чужие компании |
| Сервер дашборда: администрирование | Проверенные операции изменения оформления, назначение доступа своей компании, аудит | Произвольный SQL; секреты; изменение CORE |
| Развёртывание | Применение проверенных изменений структуры и прав | Повседневная работа бота под этими правами |
| Павел как администратор инфраструктуры | Обслуживание общей БД и восстановление | Передача своего доступа клиентам |

Имя роли содержит код компании и среду, например **k001_prod_bot**. Реальные пароли хранятся в Credentials или серверных секретах.

## Защита на стороне БД

1. Выдать USAGE только своей schema и точные права на нужные объекты.
2. Отозвать ненужные права PUBLIC, anon, authenticated и EXECUTE у функций. Не копировать примеры с GRANT ALL.
3. Вызовы ограниченных функций используют фиксированную schema; её имя никогда не приходит из LLM, Telegram или параметра браузера.
4. Значения запросов передаются параметрами. Названия объектов выбираются только из доверенной конфигурации.
5. Функции с повышенными правами, если необходимы для узкой операции, принадлежат отдельной роли компании, проверяют вызывающую роль, используют безопасный search_path и не принимают произвольный SQL.
6. Клиентский бот получает знания только через функцию поиска активной версии. Прямого SELECT по черновикам и оригиналам у него нет.
7. Представления и функции дашборда не должны обходить ограничения за счёт владельца. Проверять фактическое поведение под ролью приложения.
8. При будущей публикации таблиц в Data API обязательны отдельный пересмотр доступа, grants и RLS. Это изменение архитектуры, а не настройка при обычном копировании.

service_role обходит RLS; создание нескольких Credentials с одним таким ключом не изолирует компании. Даже новый отдельный ключ с той же привилегированной ролью не заменяет ограничения БД.

## Авторизация дашборда

Для v1 используется общий сервис Auth серверного Supabase. Сервер проверяет подпись/срок/издателя токена и членство пользователя в конкретной компании. Роль «Павел/разработчик» определяется серверной записью прав, а не полем запроса или скрытой кнопкой.

Сам факт входа через Auth не даёт доступа к любой компании. Сервер конкретного дашборда закреплён за своей schema. Нельзя передать другую schema или kompaniya_id в URL и получить чужие данные.

Чтение и административная запись используют разные подключения. Руководитель не может вызвать административную операцию через прямой HTTP-запрос. Доступ отзывается на сервере; действия Павла записываются в журнал.

## Остальные границы

- У каждого служебного бота свои token, разрешённые user ID и chat ID. В v1 загрузка — из разрешённого личного чата Павла; расширение списка фиксируется при внедрении.
- Подлинность webhook проверяет адаптер до приёма данных. Один лишь переданный user ID не является доказательством подлинности запроса.
- TLS/приватная сеть защищают соединения. PostgreSQL и Studio не открываются клиентам.
- Оригиналы Markdown в v1 хранятся внутри schema компании, не в общем открытом bucket и не в GitHub.
- Ключ памяти, логи и очереди содержат границу компании и среды. Сведения другой компании не попадают в запрос к LLM.
- Клиенты не получают доступ к общей панели n8n. Настройка прав в самой БД не защищает от администратора сервера; Павел — доверенный владелец инфраструктуры.

## Проверки допуска

Будущие тесты выполняются настоящими прикладными ролями, а не postgres:

- А читает и изменяет только разрешённые данные А; Б — только Б.
- А не может читать/изменять таблицы Б, вызывать функции Б или открыть документ Б.
- Подмена компании в HTTP, Telegram, поиске и ключе памяти не даёт доступ.
- Бот не видит черновики и оригиналы; служебный процесс не читает сырые диалоги.
- Неавторизованный посетитель не получает диалоги; руководитель не выполняет операции Павла.
- Тестовая роль не пишет в рабочую schema.
- Проверены новые таблицы/функции: права по умолчанию не открывают доступ.

До успешного выполнения этих проверок изоляция считается описанной, но не доказанной.
