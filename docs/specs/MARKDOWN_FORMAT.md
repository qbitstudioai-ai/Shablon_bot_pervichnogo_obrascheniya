# Формат Markdown и подготовка фрагментов

## Почему Markdown

Для первой версии Markdown удобен: понятные заголовки, списки и таблицы, читаемый исходник, отсутствие зависимости от верстки PDF/Word. Это инженерный выбор для текстовых знаний, а не утверждение, что LLM всегда лучше работает только с .md.

Сканы, схемы и сложные таблицы требуют отдельного извлечения и проверки; смена расширения PDF на .md не преобразует документ. В v1 служебный бот принимает только подготовленный Markdown. Преобразование других форматов можно добавить отдельной задачей.

Павел может передать исходные материалы ChatGPT для подготовки полного .md; писать SQL/код для этого ему не требуется.

## Формат файла

UTF-8, один YAML-блок в начале, один H1 в содержимом. H1 совпадает по смыслу с nazvanie. H2 — разделы, H3–H6 — последовательные подразделы без пропуска уровней. Заголовки внутри кодовых блоков не считаются структурными заголовками.

Обязательны:

| Поле YAML | Правило |
|---|---|
| identifikator_dokumenta | Постоянный ID: строчные латинские буквы, цифры и _, начинается с буквы, до 80 символов |
| nazvanie | Непустое название |
| tip_dokumenta | opisanie, harakteristiki, instrukciya, faq, usloviya, politika |

Дополнительно: versiya_istochnika, data_obnovleniya (YYYY-MM-DD), kontrolnye_voprosy. Идентификатор документа — значение поля, не имя SQL-объекта, поэтому его предел отличается от 63 байт для имён БД.

Для автоматической первой публикации нужны 3–10 вопросов. Каждый содержит vopros и ozhidaemyy_razdel; ozhidaemyy_fakt необязателен. Они извлекаются в отдельные записи проверки, не включаются в embeddings. Без вопросов документ можно принять, но нельзя автоматически опубликовать.

Пример: [baza-znaniy-shablon.md](../../templates/baza-znaniy-shablon.md). Это учебный документ с вымышленными данными, не готовая база компании. Перед загрузкой заменить весь пример.

## Очистка без изменения смысла

Разрешены нормализация переводов строк/BOM, осторожная нормализация Unicode, удаление HTML-комментариев, script/style и пустых декоративных элементов вне кодовых блоков. YAML отделяется от поискового текста, его важные поля остаются в метаданных и смысловом хэше.

Нельзя:

- глобально сжимать пробелы, ломая вложенные списки, код или таблицу;
- удалять повторяющийся факт под разными моделями/заголовками;
- удалять «лишние» числа, цены, оговорки или единицы;
- исправлять противоречивые характеристики догадкой LLM;
- автоматически открывать ссылки/скачивать изображения из документа;
- исполнять HTML, команды, YAML-теги или инструкции из текста.

Навигация/оглавление удаляются только если структурно распознаны как навигация. Неоднозначный блок сохраняется с предупреждением либо файл возвращается на исправление. Неверные уровни заголовков не исправляются по догадке.

Сохраняются оригинал и отчёт очистки: удалённые типы блоков, предупреждения и версия обработчика. Куратор должен иметь возможность сравнить исходник и подготовленный текст.

## Структурное деление

Начальный профиль v1: целевой размер **600 токенов**, максимум **800 токенов**, перекрытие **100 токенов** при разрезании длинного раздела. Это стартовые параметры проекта; менять их можно после контрольных вопросов с новой версией обработки.

Токены считаются токенизатором выбранной embedding-модели для окончательного текста: название, путь раздела, повторённый заголовок таблицы/вопрос и само содержание. Символы не считаются токенами. Лимиты модели также проверяются независимо.

Порядок:

1. Разобрать Markdown структурным парсером.
2. Сохранить путь H1 > H2 > … и исходную последовательность.
3. Делить внутри смыслового раздела по абзацам/предложениям.
4. Небольшой фрагмент до 80 токенов можно объединить только внутри той же темы/модели; короткий самостоятельный ответ допустим без объединения.
5. Перекрытие не переносить через границу другого товара/темы.
6. К каждому фрагменту добавить контекст заголовков и проверить окончательный размер.

FAQ: вопрос и ответ сохраняются вместе, пока помещаются в максимум. Длинный ответ делится по смыслу; вопрос и путь повторяются в каждой части.

Таблица: деление по группам строк с повторением заголовка и единиц. Одна слишком длинная строка может быть детерминированно превращена в пары «поле: значение» с идентификатором товара; если всё равно не помещается, запросить разделение источника. Не обрезать данные молча.

Код/неразделимый блок свыше максимума возвращается автору для переработки. Ограничение размера имеет приоритет над правилом «целый блок», но не разрешает потерю содержания.

## Реализация позже

n8n должен применять ровно один подготовленный алгоритм деления. Нельзя после него включить ещё стандартный splitter, который повторно разрежет фрагменты и потеряет метаданные.

Пакетная обработка обязана сохранять принадлежность каждого фрагмента; нельзя подставлять метаданные первого элемента всем остальным. n8n [документирует такую особенность выражений в поднодах](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.documentdefaultdataloader/).

Конкретные parser/tokenizer и доступность модулей в self-hosted n8n фиксируются в PRE-02. [Code node допускает настройку внешних модулей на собственном сервере](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.code/). Не считать эти модули уже установленными.

## Как обновить документ

Оставить identifikator_dokumenta, изменить факты и необходимые метаданные, проверить вопросы, повторно отправить .md. Для другого логического документа использовать новый ID. Правила дублей и публикации находятся в [KNOWLEDGE_INGESTION.md](KNOWLEDGE_INGESTION.md).
