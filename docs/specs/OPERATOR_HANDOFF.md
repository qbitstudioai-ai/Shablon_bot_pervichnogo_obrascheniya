# Перехват диалога человеком и операторский Telegram

Статус: нормативная спецификация v0.3. Описывает переносимый операторский интерфейс шаблона. Реальный Telegram, Credentials, PostgreSQL-функции и production-трафик этой спецификацией не включаются.

## Основное решение

Для v1 обязательным переносимым интерфейсом живого менеджера является **закрытая служебная Telegram-супергруппа компании с включёнными темами**.

У каждой компании два Telegram-назначения:
- клиентский бот принимает личные сообщения покупателей;
- служебный бот работает с сотрудниками, операторской группой, уведомлениями и служебными действиями.

Один служебный бот использует один согласованный webhook-вход. Конкурирующие webhook на один bot token не создаются.

После Take текущий диалог остаётся у закреплённого менеджера. Обязательного Return или обязательного ручного completion сейчас нет. Клиентская переписка после Take ведётся только через тему общей служебной группы.

## Один клиентский диалог — одна тема

Тема создаётся с первого принятого сообщения нового клиентского диалога.

Постоянная связь хранится в БД:

`dialog_id ↔ sluzhebnyy_chat_id ↔ message_thread_id`.

В тему зеркалируются:
- входящие сообщения клиента;
- подтверждённо отправленные ответы бота;
- важные системные события;
- факт запроса человека;
- факт успешного Take и имя менеджера;
- последующие сообщения клиента после Take.

Зеркало является интерфейсом сотрудников. Источник истины — Supabase.

## Когда нужен человек

Human-needed создаётся минимум при:
- прямой просьбе клиента;
- подтверждённом конфликте/негативе;
- невозможности дать подтверждённый ответ по знаниям;
- небезопасной технической ситуации;
- другом разрешённом бизнес-событии компании.

При human-needed происходят **два независимых действия**:

1. В теме клиента общей группы появляется заметный сигнал, например **«🚨 Нужен менеджер»**, с кнопкой **«Забрать диалог»**.
2. Всем разрешённым активным менеджерам, у которых включены личные уведомления и подтверждён private chat, служебный бот отправляет личное важное уведомление о том, что клиенту нужен менеджер.

Личный чат служебного бота **не используется для ведения клиентской переписки**. Его назначение — срочно привлечь внимание менеджеров.

Для личных уведомлений менеджер заранее запускает `/start` в личном чате со служебным ботом. Подтверждать private chat можно только для менеджера, который уже есть в доверенном списке компании. Неизвестный Telegram user автоматически менеджером не становится.

Workflow не принимает произвольный private chat ID из клиентского текста. Получатели личных уведомлений определяются только из доверенных данных БД.

## Захват диалога

Нажатие **«Забрать диалог»** атомарно меняет владельца:

`bot → chelovek`.

Одновременно фиксируется конкретный менеджер. Если несколько сотрудников пытаются забрать один диалог, successful first commit выигрывает; остальные получают конфликт/состояние «уже занят».

Кнопка Take может быть нажата из сообщения служебного бота, но после успешного Take рабочая переписка всё равно продолжается только в теме общей группы.

После успешного Take:
- новые автоматические ответы бота не отправляются;
- готовящийся AI-ответ отбрасывается финальной проверкой владельца;
- напоминания/ожидания бота отменяются или не запускаются;
- новые клиентские сообщения продолжают сохраняться и зеркалироваться в ту же тему;
- на новых зеркальных сообщениях кнопка «Забрать диалог» больше не показывается;
- только текущий закреплённый менеджер имеет право отправлять реплики клиенту;
- в теме группы видно публичное событие вида **«👤 Диалог переключён на <имя менеджера>»**.

## Переписка менеджера

Менеджер пишет обычный текст **в теме клиента общей служебной группы**.

Служебный workflow:
1. определяет тему;
2. проверяет, что диалог принадлежит человеку;
3. проверяет, что автор сообщения — текущий закреплённый менеджер;
4. проверяет актуальную версию диалога;
5. создаёт durable manual outgoing intent;
6. клиентский sender отправляет реплику через клиентского Telegram-бота;
7. внешний результат подтверждается отдельно.

Клиент продолжает видеть один и тот же личный чат с клиентским ботом.

Ручная отправка подчиняется тем же правилам надёжности, что и автоматическая: intent сохраняется до внешнего API, confirmed/unknown/error фиксируются после API, неоднозначный результат не повторяется вслепую.

## Личные уведомления менеджерам

Личное уведомление — это только alert, а не второй интерфейс переписки.

Требования:
- один human-needed может создать уведомления нескольким менеджерам;
- eligible manager: активен, личные уведомления включены, private chat подтверждён;
- fan-out выполняется внутри доверенного DB API;
- caller не передаёт manager UUID/private chat ID;
- повтор того же alert должен быть идемпотентным;
- отсутствие eligible managers не ломает основной групповой handoff;
- групповой сигнал остаётся обязательным источником видимого состояния для команды.

## Голос, фото и видео

### Голос

Сырое аудио не отправляется во внешний STT по умолчанию. Порядок v1:
1. исходное событие сохраняется локально;
2. файл скачивается клиентским Telegram Credential;
3. локальный STT получает аудио;
4. расшифровка сохраняется как производный текст;
5. выполняется локальная PII-очистка;
6. только очищенный текст может идти во внешний LLM/embedding API;
7. голосовое сообщение зеркалируется менеджеру в тему.

Если голос не удалось распознать, бот предлагает позвать менеджера.

### Фото и видео

Фото и видео не передаются в vision/LLM/embedding автоматически.

Если информация на вложении важна, бот предлагает подключить менеджера. Сам файл должен быть доступен менеджеру в операторской теме через безопасный адаптер.

## CRM и дашборд

CRM — дополнительный адаптер. Недоступность CRM не должна ломать операторский Telegram handoff.

Дашборд предназначен для аналитики, истории, качества, настроек и контроля; он не является обязательным окном для получения срочных уведомлений о клиентах.

## Надёжность операторского зеркала

Требования:
- тема одного диалога создаётся идемпотентно;
- повтор worker не создаёт вторую тему;
- одно сообщение не превращается в несколько одинаковых зеркал;
- сбой служебного Telegram не отменяет факт принятого клиентского входа;
- human-needed имеет повышенный приоритет;
- перед ручной отправкой повторно проверяются тема, владелец, менеджер и версия диалога;
- private alerts создаются durable и идемпотентно;
- direct runtime table DML от bot/service ролей не требуется.

## Настройки при внедрении

Для новой компании меняются:
- ID закрытой служебной forum-группы;
- служебный Telegram Credential;
- список разрешённых менеджеров;
- включены ли личные уведомления каждому менеджеру;
- приоритет менеджера;
- подпись/формат названия темы;
- локальный STT adapter и лимиты;
- CRM adapter при наличии.

Секреты, bot token, реальные Telegram ID сотрудников и реальные переписки в публичный шаблон не сохраняются.

## Проверки до production

Обязательны сценарии:
- первый вход создаёт ровно одну тему;
- последующие входы используют ту же тему текущего диалога;
- клиентские и подтверждённые bot messages появляются в правильной теме;
- human-needed создаёт групповой сигнал;
- human-needed создаёт личные alerts всем eligible managers;
- менеджер без подтверждённого private chat не получает alert;
- неизвестный Telegram user не может зарегистрировать себя как manager через `/start`;
- два менеджера одновременно нажимают Take — владелец один;
- после Take поздний AI-ответ не отправляется;
- после Take напоминания/активные bot jobs отсутствуют;
- чужой менеджер не может отправить реплику клиенту;
- ручной текст текущего менеджера доходит клиенту;
- новые клиентские сообщения после Take зеркалируются в ту же тему;
- рабочая переписка менеджера не переносится в личный чат;
- падение служебного Telegram не теряет клиентский вход и не создаёт дублей после восстановления.

## Проверенные возможности Telegram

Проект опирается на официальные возможности Bot API:
- forum topics;
- `message_thread_id`;
- inline keyboard/callback query;
- private messages служебного бота после того, как менеджер сам начал с ним диалог.

В текущем TEST n8n встроенная Telegram-нода не предоставляет `createForumTopic`; для создания темы используется отдельный минимальный TEST bridge к официальному Bot API. Он не должен хранить Supabase-доступ и не создаёт competing webhook.
