# Перехват диалога человеком и операторский Telegram

Статус: нормативная спецификация v0.1. Описывает переносимый операторский интерфейс шаблона. Реальный Telegram, Credentials, PostgreSQL-функции и production-трафик этой спецификацией не включаются.

## Основное решение

Для v1 обязательным переносимым интерфейсом живого менеджера является **закрытая служебная Telegram-супергруппа компании с включёнными темами (forum topics)**. CRM и дашборд могут дополнять этот интерфейс, но способность человека увидеть разговор и забрать его не должна зависеть от открытой страницы браузера или конкретной CRM.

У каждой компании остаются два разных Telegram-назначения:

- клиентский бот принимает личные сообщения покупателей;
- служебный бот работает с сотрудниками, операторской группой, уведомлениями и служебными действиями.

Один служебный бот использует один согласованный webhook-вход. Операторские callback/сообщения и будущая загрузка знаний маршрутизируются после одного надёжного входа в нужные логические ветки; конкурирующие webhook разных workflow на один токен не создаются.

## Один клиент — одна тема

Тема создаётся **с первого принятого сообщения нового клиентского диалога**, а не только при возникновении проблемы.

Постоянная связь хранится в БД:

`dialog_id ↔ sluzhebnyy_chat_id ↔ message_thread_id`.

В теме с самого начала зеркалируются:

- входящие текстовые сообщения клиента;
- подтверждённо отправленные ответы бота;
- голосовые сообщения клиента для прослушивания менеджером;
- фото и видео клиента для просмотра менеджером;
- системные события, важные для оператора: запрос человека, конфликт, недостаток знаний, захват и возврат управления.

Зеркало является представлением разговора для сотрудников. Источником истины остаётся Supabase; удаление сообщения из служебной группы не удаляет архив диалога.

Создание темы и зеркалирование выполняются после долговечной регистрации клиентского входа. Ошибка Telegram-группы не откатывает уже принятый клиентский вход и не должна заставлять Telegram клиента бесконечно повторять webhook.

## Карточка темы

После создания темы служебный бот отправляет в неё карточку, например:

- клиент/безопасная подпись;
- канал;
- текущий этап;
- владелец: бот или человек;
- важные неперсональные признаки;
- кнопка **«Забрать диалог»**.

Карточка не является хранилищем состояния. Актуальное право отправки всегда проверяется в БД непосредственно перед сообщением клиенту.

## Когда нужен человек

Сигнал о необходимости человека создаётся минимум при:

- прямой просьбе клиента;
- подтверждённом конфликте/негативе;
- невозможности дать подтверждённый ответ по знаниям, если уточнение не решает проблему;
- технической ситуации, в которой автоматический ответ небезопасен;
- фото/видео, если клиент подтверждает, что находящаяся там информация важна;
- другом настраиваемом бизнес-событии компании.

Сигнал появляется в теме клиента. Дополнительно, если для компании включены личные уведомления, служебный бот отправляет его назначенному менеджеру в личный Telegram с кнопкой **«Забрать диалог»**.

Для личных уведомлений менеджер должен заранее начать диалог со служебным ботом; система хранит разрешённый Telegram user ID и подтверждённый private chat ID. Нельзя пытаться отправлять личные уведомления произвольным Telegram ID из клиентского текста.

## Захват диалога

Нажатие **«Забрать диалог»** не является только интерфейсной кнопкой. PostgreSQL атомарно проверяет текущее состояние и меняет владельца:

`bot → chelovek`.

Одновременно фиксируется конкретный менеджер. Если два сотрудника нажали почти одновременно, успешен только первый commit. Второй получает сообщение, что диалог уже занят.

После успешного захвата:

- новые автоматические ответы не отправляются;
- готовящийся AI-ответ отбрасывается при финальной проверке владельца;
- напоминания отменяются/не запускаются;
- новые сообщения клиента продолжают сохраняться и зеркалироваться в ту же тему;
- только закреплённый менеджер имеет право отправлять реплики клиенту через операторскую тему.

Сотрудник пишет обычное текстовое сообщение в теме. Служебный workflow определяет тему, проверяет владельца и менеджера, создаёт безопасное исходящее действие и отправляет текст клиенту через клиентского Telegram-бота. Клиент продолжает видеть тот же личный чат с компанией.

Ручная отправка подчиняется тем же правилам надёжности, что и автоматическая: намерение сохраняется до API, результат подтверждается после API, неизвестная доставка не повторяется вслепую.

## Возврат боту

Возврат выполняется только явной кнопкой **«Вернуть боту»** и отдельным событием. Автоматический таймер возврата запрещён.

После возврата:

- владелец меняется `chelovek → bot`;
- ручная часть разговора остаётся в истории и памяти;
- бот не обязан немедленно писать клиенту;
- обычный режим возобновляется со следующего подходящего входа клиента после загрузки актуальной памяти.

## Текст, голос, фото и видео

### Текст

Текст клиента проходит обычный CORE: PII, память, guard, RAG и продажи. Текст менеджера в операторской теме после захвата направляется клиенту.

### Голос

Голос клиента поддерживается ботом, но **сырое аудио не отправляется во внешний STT по умолчанию**, потому что внутри могут находиться имя, телефон, адрес и другие PII.

Порядок v1:

1. исходное Telegram-событие сохраняется локально;
2. файл скачивается клиентским Telegram Credential;
3. локальный STT-адаптер на российском сервере получает аудио;
4. расшифровка сохраняется как производный текст;
5. локальная PII-очистка выполняется над расшифровкой;
6. только очищенный текст может идти во внешний LLM/embedding API;
7. исходное голосовое зеркалируется менеджеру в тему.

Конкретный локальный STT-движок и его производительность должны быть выбраны и проверены до production. URL из draft workflow является настройкой/контрактом, а не доказательством развёрнутого сервиса.

Если голос не удалось распознать или он выходит за допустимые лимиты, это не нарушение клиента: бот предлагает позвать менеджера.

### Фото и видео

Фото и видео **не передаются в vision/LLM/embedding и не анализируются ботом**.

Бот отвечает клиенту смыслом:

> «Я не могу распознать информацию на фото или видео. Если там важная информация, я могу позвать менеджера. Позвать?»

и показывает кнопки **«Позвать менеджера»** / **«Продолжить без менеджера»**.

Сам файл сохраняется как часть входного события/метаданных и зеркалируется в операторскую тему через служебного бота, чтобы человек мог его увидеть. Так как Telegram file_id относится к конкретному боту, перенос между клиентским и служебным ботом выполняется как скачивание клиентским ботом и повторная отправка служебным ботом.

### Прочие вложения

Документы, стикеры и другие неразрешённые форматы не подаются в AI автоматически. Клиент получает понятное сообщение о поддерживаемых форматах. Отдельные типы можно добавлять адаптером после проверки безопасности и бизнес-необходимости.

## CRM и дашборд

CRM — дополнительный адаптер. Для компании с Bitrix24 можно создавать/обновлять контакт, лид/сделку, этап, ответственного и другие разрешённые поля, но перехват клиента не должен ломаться при недоступности CRM.

Дашборд предназначен прежде всего для руководителя: аналитика, история, качество, настройки и контроль. Он не является обязательным окном, которое сотрудник должен держать открытым ради уведомления о клиенте.

## Надёжность операторского зеркала

Зеркалирование идёт через отдельные долговечные задания/события. Для каждого события есть стабильный ключ, статус, попытки и внешний Telegram message ID при успехе.

Требования:

- тема одного диалога создаётся идемпотентно;
- повтор worker не создаёт вторую тему;
- одно сообщение диалога не превращается в несколько одинаковых сообщений оператору;
- сбой зеркала не меняет факт приёма клиентского сообщения;
- сигнал о передаче человеку имеет повышенный приоритет и при исчерпании повторов создаёт техническое событие;
- перед ручной отправкой повторно проверяются тема, владелец, менеджер и версия диалога.

## Настройки при внедрении

Для новой компании меняются, а CORE не переписывается:

- ID закрытой служебной forum-группы;
- служебный Telegram Credential;
- разрешённые менеджеры;
- правило назначения ответственного;
- включены ли личные уведомления;
- подпись/формат названия темы;
- локальный STT adapter и лимиты голоса;
- CRM adapter при наличии.

Секреты, bot token и реальные ID сотрудников не хранятся в публичном шаблоне.

## Проверки до production

Обязательны сценарии:

- первый вход создаёт ровно одну тему;
- последующие входы используют ту же тему;
- текст клиента и подтверждённый текст бота появляются в правильной теме;
- фото/видео видит менеджер, но они не уходят в AI;
- голос локально распознаётся, очищается от PII и только потом идёт во внешний AI;
- ошибка STT предлагает человека;
- личный сигнал приходит разрешённому менеджеру;
- два менеджера одновременно нажимают «Забрать» — владелец один;
- после захвата поздний AI-ответ не отправляется;
- чужой менеджер не может отправить реплику клиента;
- ручной текст доходит через клиентского бота и фиксируется;
- «Вернуть боту» не вызывает самопроизвольного сообщения;
- падение служебного Telegram не теряет клиентский вход и не создаёт дублей после восстановления.

## Проверенные возможности Telegram

Проект опирается на официальные возможности Bot API:

- создание forum topic: https://core.telegram.org/bots/api#createforumtopic
- отправка в конкретную тему через `message_thread_id`: https://core.telegram.org/bots/api#sendmessage
- inline-кнопки и `callback_data`: https://core.telegram.org/bots/api#inlinekeyboardbutton
- callback query: https://core.telegram.org/bots/api#callbackquery
- получение файла: https://core.telegram.org/bots/api#getfile

В n8n 2.41.0 штатная Telegram-нода поддерживает `message_thread_id`, inline keyboard, callback answer и скачивание файла. Отдельной операции `createForumTopic` в этой версии ноды не найдено, поэтому draft вызывает официальный Bot API через HTTP Request с Telegram Credential.
