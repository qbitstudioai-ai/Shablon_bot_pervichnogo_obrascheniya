# Правила обмена между компонентами

Версия внутреннего формата: **1**. Это требования к будущей реализации, не готовые API, SQL или JSON workflow. Изменение значения поля требует обновления этого документа и потребителей.

## Общие правила

Время передаётся в ISO 8601 с часовым поясом, в БД — timestamptz/UTC. Внешние идентификаторы — строки, даже если состоят из цифр. Технические UUID не подменяют внешние ID.

Каждая операция имеет **operaciya_id** и **versiya_formata**. Повтор с тем же ключом и тем же содержимым возвращает прежний результат. Тот же ключ с другим содержимым — конфликт, не молчаливое перезаписывание.

Общий ответ содержит: **operaciya_id**, **rezultat** (uspeshno, dublikat, povtorit, konflikt, otkaz, neizvestno), **kod_oshibki**, безопасное **opisanie**, **povtor_posle** при необходимости. «Неизвестно» означает отсутствие надёжного подтверждения внешнего действия, а не разрешение немедленно повторить его.

Компания, среда и schema определяются доверенным серверным экземпляром. Поля этих значений во входном сообщении пользователя игнорируются.

## 1. Канал → входной адаптер → n8n

| Внутреннее поле | Назначение |
|---|---|
| versiya_formata | Число 1 |
| kompaniya_kod, sreda | Проставляет сервер; не доверять значениям клиента |
| kanal, akkaunt_kanala_id | Код канала и конкретный аккаунт/бот |
| vneshnee_sobytie_id | Устойчивый ID события; включает тип события, если API переиспользует ID |
| vneshniy_polzovatel_id, vneshniy_dialog_id | Адрес исходного пользователя и диалога |
| vneshnee_soobshchenie_id | ID сообщения у провайдера |
| vremya_istochnika, vremya_priema | Время канала и приёма системой |
| tip_sobytiya, tip_soobshcheniya | Новое сообщение, правка, служебное событие; текст или вложение |
| tekst_ishodnyy, vlozheniya | Исходное содержание; ссылки на вложения не скачиваются без проверки |
| otvet_na_id | Связь с предыдущим сообщением, если есть |
| trassirovka_id | Связь с выполнением n8n и журналом |

Уникальный ключ входа: компания/среда + канал + аккаунт + внешний ID события. Telegram update_id без ID бота недостаточен. Для сайта сервер проверяет подписанную сессию, а клиент передаёт стабильный ID отправки для безопасного повтора.

Неподдерживаемый тип сообщения сохраняется с понятным результатом; не трактуется как пустая фраза клиента. Для Telegram v1 текст обрабатывается CORE; голос распознаётся локальным STT до внешнего AI; фото/видео не анализируются AI и предлагают передачу человеку, при этом медиа доступно оператору. Документы/стикеры по умолчанию не подаются в AI.

## 2. Регистрация входа → БД

Одна операция регистрирует событие, пользователя/идентичность, сообщение, задание обработки и отмену устаревшего ожидания. Результат: **polzovatel_id**, **dialog_id**, **soobshchenie_id**, **zadanie_id**, **versiya_dialoga**.

Новый ввод после завершения маршрутизируется по жизненному циклу; служебный callback или повтор webhook не создаёт возвращение.

Подтверждение приёма webhook допускается только после записи в долговечное хранилище. Если стандартный Trigger отвечает провайдеру раньше, его нельзя считать надёжным приёмником без проверенного сохранения входа. Это обязательная проверка PRE-01 и RT-01: при необходимости нужен сохраняющий входной адаптер либо подтверждённое восстановление из истории API. Непроверенный ранний HTTP 200 — запрет допуска к production.

## 3. БД → n8n → память и LLM

Вход обработки: ID диалога, задания и зафиксированная версия состояния. Выход памяти: **rezyume**, **poslednie_soobshcheniya**, **podtverzhdennye_fakty**, **obrabotano_do_id**, **versiya_pamyati**.

В LLM передаются только нужные обезличенные сообщения, разрешённые знания, состояние и инструкции. Телефоны/контакты для CRM остаются в защищённых данных; в контексте можно использовать метку «телефон получен». Запрос на реальные данные ограничивается необходимостью задачи.

Ответ LLM — предложение, которое проверяет CORE:

| Поле | Значение |
|---|---|
| tekst_otveta | Текст для клиента |
| deystvie | prodolzhit, sprosit, peredat, zavershit, utochnit_otkaz |
| ozhidaetsya_otvet | Нужно ли содержательное продолжение клиента |
| predlozhennyy_etap | Код этапа из разрешённого списка |
| predlozhennye_celi | Цели с доказательствами из сообщений/интеграций |
| istochniki_znaniy | ID версии и фрагмента для технической проверки |
| uverennost | Оценка модели, не факт и не самостоятельное разрешение действий |

Адресаты, schema, SQL и команды публикации знаний в ответе LLM не принимаются. Фраза из документа знаний считается материалом, а не системной командой. При нехватке знаний бот уточняет вопрос или передаёт человеку; характеристики не выдумываются.

## 4. Поиск знаний

Основной путь: n8n создаёт вектор вопроса через выбранный embedding API и вызывает ограниченную функцию PostgreSQL. Модель и размерность вопроса совпадают с опубликованным индексом.

Вход: **vektor_zaprosa**, **profil_indeksa_id**, **limit_rezultatov**, **porog_shodstva**. Выход каждого результата: **dokument_id**, **versiya_id**, **fragment_id**, **nazvanie**, **put_razdela**, **tekst_fragmenta**, **shodstvo**.

Сходство определено как 1 минус cosine distance. Отбираются результаты со сходством не ниже порога, сортируются по убыванию. Порог и лимит калибруются на контрольных вопросах; не копируются без проверки.

Права и фильтр активной версии применяются внутри функции до ограничения числа результатов. У клиентской функции нет аргумента «показать черновики».

Проверочный поиск — другая ограниченная операция служебной роли: дополнительно принимает конкретную **versiya_id** черновика. Он не меняет видимость клиентскому боту.

Стандартная Supabase Vector Store-нода с ожидаемыми полями content/metadata/embedding не является обязательной частью v1. Выбран путь через Postgres и явные поля, поэтому транслитерация не зависит от предположений о совместимости LangChain. Замена пути требует отдельного теста форматов и прав.

## 5. n8n → канал и CRM

До внешнего запроса сохраняется исходящее действие. Вход адаптера отправки: **deystvie_id**, сохранённые **kanal**, **akkaunt_kanala_id**, **vneshniy_dialog_id**, текст, **otvet_na_id**, ключ повтора, **versiya_dialoga**.

Результат: статус операции, внешний ID сообщения, время принятия каналом, ошибка/Retry-After. Принятие API не называется прочтением пользователем. Доставка и прочтение фиксируются отдельно, если канал сообщает их.

CRM получает минимально необходимые контактные данные, подтверждённую потребность, идентификаторы пользователя/диалога и стабильный внешний ключ заявки. Вернёт внешний ID, статус подтверждения и ошибку. Повторная попытка сначала проверяет внешний ключ; возможности идемпотентности зависят от CRM.

Режим CRM_TYPE=net сохраняет локальную заявку и задачу уведомления назначенному сотруднику. Нельзя обещать назначенное время замера без подтверждённой записи.

## 6. Клиентский диалог → операторский Telegram

Операторское зеркало использует закрытую forum-супергруппу и служебного бота компании. Для первого входа диалога создаётся постоянная связь **dialog_id → sluzhebnyy_chat_id → message_thread_id**. Повторная обработка должна вернуть существующую тему, а не создать новую.

Событие зеркала содержит: стабильный ID, dialog_id, необязательный soobshchenie_id, тип события, безопасную подпись клиента, целевые chat/thread ID, текст либо метаданные клиентского вложения, число попыток и статус. Адрес группы/темы берётся только из доверенного состояния.

В операторскую тему передаются:
- исходный текст клиента с явной меткой автора;
- только подтверждённо отправленный текст бота;
- фото/видео/голос клиента для просмотра/прослушивания человеком;
- сигналы передачи, захвата и возврата.

Фото/видео не отправляются в AI. Голос для AI сначала проходит локальный STT, затем PII-очистку; исходный голос может отдельно зеркалироваться человеку. Telegram file_id клиентского бота не считается переносимым на служебного бота: адаптер скачивает файл клиентским Credential и повторно загружает служебным.

Callback **take:<dialog_id>** вызывает атомарный захват: проверяются разрешённый менеджер и актуальный владелец; успешен только первый конкурентный запрос. Callback **return:<dialog_id>** разрешён текущему владельцу/администратору и создаёт отдельное событие возврата.

Текст сотрудника в forum topic принимается служебным webhook. По chat_id + message_thread_id определяется dialog_id; затем проверяются владелец и manager Telegram ID. Только после этого создаётся обычное исходящее действие клиентского канала. Результат отправки сохраняется так же, как у автоматического ответа.

Когда CORE требует человека, кроме сообщения в теме допускается личный сигнал разрешённому менеджеру. Private chat ID считается действующим только после того, как сотрудник сам начал диалог со служебным ботом.

Один токен служебного Telegram-бота имеет один согласованный webhook-вход. Операторские события, callbacks и будущая загрузка знаний расходятся по внутренним веткам/подworkflow после этого входа.

Полный контракт: [OPERATOR_HANDOFF.md](OPERATOR_HANDOFF.md).

## 7. Служебный Telegram → загрузка знаний

Приём: разрешённые user ID/chat ID, внешний ID события, file_id, имя, заявленный размер и MIME. Скачивание: реальные байты, фактический размер, SHA-256. MIME/расширение сами по себе не доказывают формат.

После разбора: **identifikator_dokumenta**, **nazvanie**, **tip_dokumenta**, версия/дата источника, структурный текст. Служебная роль создаёт **zagruzka_id**, **dokument_id**, **versiya_id**.

Векторизация: текст с путём заголовков, **profil_indeksa_id**, **nomer_fragmenta**, число токенов; ответ провайдера сопоставляется по индексу с исходным фрагментом, размерность и количество проверяются.

Публикация принимает **versiya_id** и **ozhidaemaya_aktivnaya_versiya_id**. При изменившейся активной версии возвращает конфликт. Публикация переключает документ, версии и состояние загрузки одной транзакцией.

Отчёт в Telegram — отдельное исходящее действие после публикации. Ошибка отчёта не отменяет успешную публикацию и не переводит её в «ошибка загрузки».

## 8. БД → сервер дашборда → браузер

Сервер проверяет вход и права, переводит границы дат из часового пояса компании в UTC, вызывает только разрешённые запросы.

Запрос отчёта: начало/конец периода, **na_moment**, канал, этап/результат, страница/курсор, версия определения метрик. Выход: показатели, знаменатели, время расчёта, применённые фильтры, полнота данных, следующий курсор. Пустой набор даёт «нет данных», процент при нулевом знаменателе — null, не деление на ноль.

Переписки возвращаются страницами; доступ к исходному тексту проверяется отдельно. На сервере и в UI текст клиента/Markdown экранируется, не выполняется как HTML или script.

## 9. Ошибки → служебный бот

Техническое событие: компания/среда, компонент, операция, уровень, код ошибки, время, ID выполнения, число повторов и безопасное описание. Сырые переписки, секреты и полный prompt исключены.

Сбой Supabase пишется в защищённый журнал вне этой БД; сбой самого n8n обнаруживает внешний монитор. Полные правила: [надёжность](RELIABILITY_AND_MEMORY.md).

Проверки всех переходов перечислены в [RELEASE_CHECKLIST.md](../RELEASE_CHECKLIST.md). Точная реализация этих контрактов создаётся позже и должна сохранять их смысл.
