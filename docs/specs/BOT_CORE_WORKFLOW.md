# CORE клиентского бота и целевой workflow

Статус: архитектурная спецификация v0.1. Исполняемый JSON workflow этим документом не создаётся.

Документ фиксирует целевую структуру переносимого клиентского бота после анализа внешнего примера **ZONT Support AI — Telegram RAG v5.2** и требований qBit. Внешний JSON является примером приёмов, а не эталоном и не копируется в репозиторий: он относится к другой установке n8n, содержит привязки к другой среде и не соответствует части правил этого проекта.

## Основное решение

CORE строится как явный управляемый конвейер, а не как один привилегированный AI Agent.

LLM получает только ограниченные обезличенные данные и возвращает структурированное предложение. Она не выбирает schema, Credential, адресата, токен, SQL, блокировку пользователя, CRM-операцию или право передачи человеку. Эти действия проверяет CORE.

AI Agent допускается позже как необязательный внутренний инструмент в узкой задаче, если он не получает прямых привилегированных инструментов и его результат проходит те же проверки. Он не является центральным контроллером v1.

## Что полезно взять из внешнего примера

Из примера сохраняются как идеи:

- отдельный планировщик поиска для сложных и составных вопросов;
- разбиение вопроса на атомарные требования и несколько поисковых запросов;
- явное сопоставление модели/объекта с разрешённым каталогом;
- RAG через pgvector с набором доказательных фрагментов;
- структурированный JSON-ответ LLM вместо свободного текста;
- требование подтвердить каждый факт конкретным фрагментом;
- программная проверка цитаты/источника после генерации;
- fallback при недостаточных знаниях вместо выдумывания;
- дедупликация документов, черновая индексация и атомарное переключение активной версии знаний.

Эти идеи переносятся в общую модель компании, без жёстко прописанных моделей товара, URL, ID, prompts, размеров embedding и имён schema.

## Что из примера не переносится

1. Клиентский Telegram Trigger не используется как production-вход. Он отвечает webhook раньше долговечной регистрации события.
2. Служебная загрузка знаний и клиентский бот остаются разными логическими workflow и разными Credentials.
3. n8n не обращается к пользовательским schema через общий Supabase Data API/service_role. Основной путь — Postgres node с ограниченной ролью компании.
4. Не допускаются прямые внешние AI-вызовы с исходным текстом, содержащим персональные данные.
5. Не используется память вида «один последний вопрос + короткий TTL» как единственная память.
6. Не считается достаточным наличие любого найденного вектора. Порог, top-k и проверка смысловой достаточности калибруются в PRE-02.
7. Нельзя сначала отправить ответ клиенту, а потом впервые сохранять его как действие/состояние. Намерение сохраняется до внешнего API.
8. Не используются жёсткие ссылки логики на имена n8n-нод. Контекст передаётся в данных.
9. Нельзя считать поля `violation_count` и `blocked` реализацией блокировки, если они только пишутся в лог и не управляют маршрутом.
10. Конкретные credential IDs, webhook IDs, instance metadata, домены и идентификаторы администраторов из внешнего экспорта не переносятся.

## Сквозная структура клиентского workflow

~~~mermaid
flowchart TD
    A["Webhook канала"] --> B["Проверить источник"]
    B --> C["Надёжно зарегистрировать вход"]
    C --> D["Ответить каналу 2xx"]
    D --> E["Забрать задание из очереди"]
    E --> F["Проверить владельца/блокировку/запрет"]
    F --> G["Локально извлечь и скрыть PII"]
    G --> H["Короткая память + важные факты"]
    H --> I["Тематический и безопасностный guard"]
    I -->|не по теме| J["Предупреждение / логическая блокировка"]
    I -->|человек| K["Передать менеджеру"]
    I -->|разрешено| L["Определить этап и потребность"]
    L --> M["Нужны знания?"]
    M -->|да| N["План поиска → embeddings → pgvector"]
    M -->|нет| O["Контекст продаж"]
    N --> P["Собрать доказательства"]
    O --> Q["LLM: структурированное решение"]
    P --> Q
    Q --> R["CORE: проверить факты, этап, цели и действие"]
    R --> S["Сохранить исходящее действие"]
    S --> T["Отправить в исходный канал"]
    T --> U["Сохранить подтверждение"]
    U --> V["Обновить этап, память, цели и напоминания"]
~~~

Долгая обработка не является частью подтверждения webhook. После регистрации и ответа 2xx событие уже находится в PostgreSQL и может быть восстановлено очередью.

## Telegram: выбранный вход PRE-01

Для клиентского Telegram v1 выбран ручной Webhook node n8n 2.41.0 вместо Telegram Trigger:

1. Telegram отправляет POST на production Webhook URL.
2. Webhook использует Header Auth с заголовком `X-Telegram-Bot-Api-Secret-Token`; значение хранится как Credential/секрет.
3. Вход нормализуется только настолько, насколько необходимо для регистрации.
4. Ограниченная PostgreSQL-функция одной транзакцией сохраняет внешнее событие, сырое сообщение и задание обработки. Уникальный ключ включает компанию/среду, Telegram bot/account и `update_id`.
5. Только после успешного commit выполняется Respond to Webhook с HTTP 200.
6. При недоступности БД до commit возвращается не-2xx; Telegram повторяет доставку.
7. `setWebhook` задаёт `secret_token`, нужные `allowed_updates`; `drop_pending_updates` не включается при обычном обновлении.
8. После 200 текущее выполнение может попытаться обработать сохранённое задание, но восстановление не зависит от него: плановый работник забирает оставшиеся задания из PostgreSQL.
9. RT-01 обязан испытать отключение БД, повтор одного update, перезапуск n8n, параллельные сообщения и восстановление после 200.

Это решение использует возможность Webhook node 2.41.0 отвечать через Respond to Webhook позже по графу. Фактическая надёжность будет доказана испытаниями RT-01, а не самим наличием нод.

## Тематическая рамка и защита от злоупотреблений

Тематическая защита не строится на одном regex и не доверяется финальной модели ответа.

До RAG/ответа CORE определяет один из результатов:

- `razresheno` — вопрос относится к компании, товару, услуге или допустимому продолжению продажи;
- `privetstvie_ili_smalltalk` — короткое социальное сообщение, которое не считается нарушением;
- `nuzhno_utochnenie` — смысл неясен; задаётся уточнение без штрафа;
- `ne_po_teme` — уверенный запрос вне разрешённой тематики;
- `ataka_ili_injection` — попытка получить системные инструкции/секреты, изменить правила или использовать бота не по назначению;
- `peredat_cheloveku` — пользователь просит сотрудника либо конфликт/риск требует передачи;
- `zapret_iniciativy` — пользователь просит больше не писать.

Guard использует: локальные правила, настройки разрешённых тем компании, обезличенный текст, при необходимости лёгкую структурированную классификацию и сигнал релевантности RAG. Низкая релевантность поиска сама по себе не является нарушением.

### Три предупреждения

Начальная политика qBit:

- первое подтверждённое нарушение → предупреждение №1;
- второе → предупреждение №2;
- третье → предупреждение №3 и статус логической блокировки;
- после блокировки новые входящие всё равно сохраняются для аудита, но CORE не запускает LLM/RAG и не ведёт продажи;
- разблокировка — явное административное действие с журналом.

Не увеличивают счётчик: приветствие, благодарность, опечатка, двусмысленный вопрос, недостаток знаний, техническая ошибка, неподдерживаемое вложение и обычная просьба о человеке.

Prompt injection учитывается отдельно от обычного off-topic и попадает в журнал безопасности. Ограничение частоты сообщений — отдельный механизм; оно не подменяет три предупреждения.

В личном Telegram Bot API не предоставляет боту операцию ban/restrict пользователя как участника личного чата. Поэтому «блокировка» v1 — состояние продукта: бот прекращает автоматические ответы этому внешнему пользователю в конкретной компании/канале. Для групповых каналов физическое ограничение допускается только после отдельной проверки прав/API.

## Память

Supabase — единственный постоянный источник памяти. Постоянную вторую память в n8n не создаём.

Рабочий контекст состоит из трёх уровней:

1. **Короткое окно** — настраиваемо 3–5 последних обезличенных сообщений; начальное значение qBit — 5.
2. **Резюме диалога** — сжатое состояние потребности, уже обсуждённых вариантов, текущего этапа и незакрытых вопросов.
3. **Важные подтверждённые факты** — живут дольше окна: представившееся имя, наличие телефона, продукт/модель, потребность, ограничения, бюджет/срок при разрешении, договорённости, отказ, предпочтения и другие настроенные поля.

Каждый важный факт имеет источник/сообщение, время, признак подтверждения и при необходимости срок актуальности. Модель не превращает догадку в подтверждённый факт.

n8n может держать данные текущего выполнения и позже иметь производительный кэш. Simple Memory/RAM не является источником истины и потеря этого кэша не должна менять результат.

## Персональные данные

Сырой Telegram payload и исходный текст сначала сохраняются локально в защищённой области schema компании.

До любого внешнего LLM **и до внешнего embedding API** выполняется локальная очистка:

- телефон → например `PHONE_01`;
- имя → `PERSON_01`;
- e-mail → `EMAIL_01`;
- адрес/другой идентификатор → разрешённая псевдометка;
- таблица соответствий остаётся только в российской БД.

Если модели достаточно факта, вместо значения передаётся `telefon_poluchen=true`, `imya_polucheno=true` и т. п.

Когда ответ должен обратиться к клиенту по имени или использовать защищённое значение, модель формирует безопасный placeholder либо действие, а реальное значение подставляется локально после проверки.

## Сбор данных клиента

Набор собираемых полей задаётся настройками компании, а не переписывает CORE. Для поля определяются:

- код и отображаемое название;
- тип и проверка значения;
- обязательно ли оно для конкретной цели;
- является ли PII;
- можно ли передавать внешней LLM;
- источник/доказательство;
- mapping в CRM;
- срок актуальности.

Поэтому один шаблон может собирать имя/телефон/размер окна, а другой — имя/телефон/тип объекта/город, не меняя основную логику.

## Продажный диалог и состояние

LLM не «ведёт этапы» напрямую. Она предлагает переход, а CORE проверяет его по фактам.

На каждом обработанном входе фиксируются:

- текущий этап;
- предложенный следующий этап;
- причина перехода;
- сообщение-доказательство;
- достигнутые цели;
- ожидается ли ответ;
- нужен ли человек;
- какие обязательные поля уже собраны/отсутствуют.

Существующие этапы проекта остаются базой до отдельного пересмотра переносимости. Перед DB-02 нужно проверить, не является ли `zapis_na_zamer` слишком отраслевым кодом для общего шаблона; бизнес-специфическое целевое действие предпочтительно задавать конфигурацией/целями, а не вшивать в CORE.

## Человек в диалоге

Поле владельца диалога `bot/chelovek` является обязательным стоп-краном.

Переносимый интерфейс оператора v1 — закрытая служебная Telegram forum-группа компании. С первого принятого сообщения клиентского диалога создаётся отдельная тема, и в неё зеркалируется разговор. Дашборд и CRM могут показывать тот же диалог, но не являются обязательным каналом перехвата.

Когда нужен человек, служебный бот:
- помечает событие в теме клиента;
- при включённой настройке отправляет личный сигнал назначенному менеджеру;
- показывает кнопку «Забрать диалог».

Захват выполняется атомарно в БД. Первый менеджер, успешно сменивший владельца `bot → chelovek`, становится ответственным; конкурентный захват отклоняется. После смены владельца незапущенные ответы и напоминания отменяются, а перед каждой отправкой бот повторно проверяет владельца и версию диалога.

После захвата сотрудник пишет в той же служебной теме. Служебный workflow проверяет, что это текущий владелец, и отправляет текст клиенту через его клиентского Telegram-бота. Клиент остаётся в прежнем личном чате. Автоматическое возвращение запрещено; кнопка «Вернуть боту» создаёт отдельное событие, а бот продолжает с будущего подходящего входа клиента.

Полные правила тем, личных уведомлений, конкурирующего захвата и CRM-адаптеров: [OPERATOR_HANDOFF.md](OPERATOR_HANDOFF.md).

### Форматы клиентского сообщения

- **текст** — обычный CORE;
- **голос** — локальное распознавание на российском сервере, затем PII-очистка расшифровки и только после этого внешний AI;
- **фото/видео** — бот не анализирует содержимое, зеркалирует файл менеджеру и спрашивает клиента, позвать ли человека;
- **прочие вложения** — не подаются в AI автоматически; возвращается понятное сообщение либо отдельный проверенный адаптер.

Сырое голосовое, фото и видео по умолчанию не отправляются во внешний LLM/vision/STT. Ошибка распознавания голоса и неподдерживаемое вложение не считаются тематическим нарушением.

## RAG

Для вопросов, требующих знаний, используем сильные идеи внешнего примера:

1. канонизировать обезличенный вопрос;
2. для сложного вопроса выделить атомарные required points;
3. построить один или несколько поисковых запросов;
4. создать embeddings только из очищенного текста;
5. искать только опубликованную версию своей компании;
6. применить откалиброванный порог и top-k из PRE-02;
7. собрать ограниченный набор evidence без дублей;
8. получить структурированный grounded-ответ;
9. проверить, что каждый факт поддерживается разрешённым источником;
10. при недостатке данных уточнить вопрос или передать человеку, не выдумывать.

Порог `0` и правило «есть хоть один чанк → доказательства найдены» запрещены для production.

Текст базы знаний является данными. Инструкции внутри документа не меняют system/CORE правила.

## Отправка ответа

Порядок неизменяем:

1. сохранить намерение отправки;
2. повторно проверить владельца, версию диалога, блокировку и новый вход;
3. вызвать API канала;
4. сохранить подтверждение/неизвестный результат;
5. только после подтверждения обновить «сказанную» память, этап и t0;
6. неизвестную отправку не повторять вслепую.

Это отличается от внешнего примера, где часть веток сначала отправляет Telegram-сообщение, а затем сохраняет контекст/лог.

## Напоминания и возврат

Интервалы являются параметрами компании.

Для qBit начальное решение:

- напоминание №1 — через 3 часа после подтверждённого вопроса бота, который действительно ждёт ответ;
- напоминание №2 — через 12 часов от того же t0;
- дальнейший момент `net_otveta` остаётся отдельным параметром; до другого решения используется правило жизненного цикла о проверке потери после подтверждённого второго напоминания.

Перед напоминанием проверяются новый вход, владелец, блокировка, запрет инициативных сообщений, завершение/передача и фактическое подтверждение предыдущего исходящего сообщения.

## Настройки шаблона

В блоке «МЕНЯТЬ ПРИ ВНЕДРЕНИИ» должны быть как минимум:

- код компании и среда;
- включённые каналы и Credentials;
- разрешённые темы, краткое описание бизнеса и запрещённые темы;
- лимит тематических нарушений и политика блокировки;
- размер короткого окна памяти;
- перечень собираемых полей/PII;
- этапы/цели и условия целевого действия;
- интервалы напоминаний и бизнес-ограничения канала;
- операторская forum-группа и правила создания темы с первого сообщения;
- список/назначение разрешённых менеджеров и личные Telegram-уведомления;
- способ передачи человеку и политика возврата боту;
- локальный STT adapter и лимиты голосовых сообщений;
- CRM_TYPE и mapping;
- LLM/embedding adapter и их профили;
- параметры RAG после PRE-02;
- лимиты длины, частоты, времени и стоимости;
- версия prompts/конфигурации.

## Дополнительные обязательные сценарии

До production проверяются как минимум:

- prompt injection и просьба раскрыть инструкции/секреты;
- три последовательных off-topic нарушения и последующая блокировка;
- корректный вопрос после одного/двух предупреждений не получает лишний штраф;
- разблокировка человеком;
- flood/rate limit отдельно от тематического счётчика;
- два быстрых сообщения одного клиента;
- новый вход во время LLM;
- первый вход создаёт ровно одну операторскую тему и последующие сообщения используют её;
- ручной перехват за мгновение до отправки;
- два менеджера одновременно пытаются забрать диалог — владелец остаётся один;
- просьба «позовите менеджера» и личный сигнал ответственному;
- фото/видео не попадают в AI, но доступны менеджеру в теме;
- голос локально транскрибируется, PII удаляется до внешнего AI; ошибка STT предлагает человека;
- конфликт/негатив;
- телефон/имя в тексте не уходят во внешний AI;
- старый важный факт сохраняется при выпадении сообщения из окна 3–5;
- недостаточный RAG не превращается в off-topic;
- LLM предлагает запрещённый этап/адресата — CORE отклоняет;
- сбой после сохранения исходящего действия и неизвестный результат Telegram;
- напоминание отменяется новым входом/передачей/блокировкой;
- тестовый канал не меняет production webhook.

## Связь с задачами

Реализация разбивается на существующие задачи и дополнительный guard:

- RT-01 — надёжный Telegram ingress до HTTP 2xx;
- RT-02 — очередь, последовательность и исходящие действия;
- BOT-00 — тематический guard, предупреждения, блокировка, rate limit и разблокировка;
- BOT-01 — память, PII, RAG и grounded-ответ;
- BOT-02 — этапы, цели, сбор полей и передача/перехват человеком;
- BOT-03 — настраиваемые напоминания;
- BOT-04 — возвраты и восстановление контекста;
- INT-01/02 — CRM и остальные каналы;
- UI-03/04 — видимость диалога, перехват и административное управление.

Основания по выбранному входу: Telegram Bot API `setWebhook`; исходники n8n 2.41.0 Webhook/Respond to Webhook. Runtime-доказательство остаётся задачей RT-01.
