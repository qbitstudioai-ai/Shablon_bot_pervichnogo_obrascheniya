# Приём и обновление знаний

Нормативные требования v0.3. Загрузка идёт через служебный Telegram-бот каждой компании. У этого бота один согласованный webhook-вход: операторские сообщения/callback и будущая загрузка .md маршрутизируются после надёжной регистрации в разные логические ветки. Полный обработчик Markdown, SQL и публикация знаний ещё не созданы.

## Идентичность и хранение

Различаются четыре объекта:

1. **Загрузка** — конкретная попытка приёма файла, включая ошибки и дубли.
2. **Документ** — постоянный identifikator_dokumenta внутри компании.
3. **Версия** — проверяемое содержимое документа и снимок параметров обработки.
4. **Фрагмент** — часть конкретной версии с вектором.

Таблицы: zagruzki_znaniy, dokumenty_znaniy, versii_dokumentov_znaniy, fragmenty_znaniy. Документ содержит единственную ссылку **aktivnaya_versiya_id**. Фрагменты не имеют независимого флага aktiven: видимость определяется ссылкой документа и опубликованным состоянием версии.

В v1 оригинальные байты .md сохраняются в защищённом поле загрузки внутри schema компании. В версии хранится ссылка на загрузку. Срок хранения оригиналов и архивов задаётся до запуска; клиентский бот оригиналы не читает.

## Приём

- Фиксированные schema/роль/токен workflow; никакого выбора компании из текста.
- Разрешённые Telegram user ID и личный chat ID; проверка подлинности события.
- UTF-8, расширение .md, безопасный структурный разбор по [MARKDOWN_FORMAT.md](MARKDOWN_FORMAT.md).
- Начальный лимит **5 MiB** фактических байтов, включая YAML. Это внутреннее ограничение проекта, не обещание лимита Telegram.
- Регистрация уникального события и попытки до затратной обработки.
- Ограниченное скачивание; реальный размер перепроверяется, поддельный MIME не принимается как доказательство.
- YAML разбирается без выполнения типов/кода; вложенные/чрезмерные структуры и дубли ключей отклоняются.
- Секреты и личные данные проверяются доступными правилами; это помогает обнаруживать признаки, но не гарантирует нахождение всех секретов. Автор обязан передавать документы без них.

Ошибки входа записываются в загрузку даже если документ/версию ещё невозможно определить.

## Хэши и повторы

**hash_istochnika** — SHA-256 исходных байтов. **hash_soderzhaniya** — SHA-256 канонического смыслового содержимого: сохранённые заголовки/абзацы/таблицы, важные поля YAML, включая название, тип, версию/дату источника и контрольные вопросы. Структура входит в расчёт; удалять YAML и сравнивать только текст недостаточно.

**otpechatok_obrabotki** учитывает hash_soderzhaniya + версию очистки/парсера/чанкинга + embedding-модель и размерность. Незначительные различия переводов строк могут не менять смысловой хэш. Любое неоднозначное отличие сохраняется как изменение, не отбрасывается.

| Ситуация в этой компании | Действие |
|---|---|
| Тот же ID события Telegram | Вернуть результат прежней попытки; повторно не обрабатывать |
| Тот же identifikator_dokumenta и отпечаток текущей активной версии | Дубль: записать попытку, сообщить об активной версии |
| Тот же документ, другое содержимое/параметры обработки | Создать новую версию |
| Совпадение только с ошибочной загрузкой | Разрешить исправленный повтор; не считать документ опубликованным |
| Совпадение с архивом | Запросить явное восстановление или создать новую проверяемую версию; не отвечать «уже активно» |
| Совпадение текста с другим идентификатором | Предупредить о возможном дубле; автоматически ничего не заменять |
| Семантически похожий документ | Только предупреждение; сходство не доказывает идентичность |

Переименование файла не меняет идентичность. Поиск дублей никогда не просматривает другую компанию и не раскрывает наличие её документов. Предупреждение о сходстве не является обязательным блокирующим шагом v1.

## Очистка и фрагменты

Правила очистки и конкретные размеры находятся только в [MARKDOWN_FORMAT.md](MARKDOWN_FORMAT.md). Сохраняются структура, факты, единицы и связь вопрос–ответ. Текст не переписывается моделью.

Embedding получает текст фрагмента вместе с названием/путём раздела. Сохраняется точный текст, который был отправлен на векторизацию, и его хэш. Векторы от разных моделей не смешиваются. Вопрос для поиска векторизуется той же моделью и размерностью.

Параметры обработки берутся из версии конфигурации n8n; в БД сохраняется неизменяемый снимок для проверки и воспроизводимости. Это не редактируемое управление поведением из БД.

## Состояния

Загрузка: poluchena, proverka, obrabotka, ozhidaet_proverki, zavershena, dublikat, oshibka.

Версия: chernovik, gotova, opublikovana, arhiv, oshibka. Только версия, указанная в aktivnaya_versiya_id, доступна обычному поиску.

Уникальны identifikator_dokumenta внутри schema и пара dokument_id + nomer_versii. Архивных версий может быть много. Ограничение «уникальны документ + boolean aktiven» не применяется.

## Порядок будущего workflow

1. Получить и надёжно зарегистрировать событие.
2. Проверить отправителя, файл и размер; сохранить оригинал и хэш.
3. Разобрать YAML и Markdown; проверить ID и структуру.
4. Рассчитать смысловой хэш и параметры обработки.
5. Найти документ и определить дубль/новую версию.
6. Поставить обработку в последовательную очередь этого документа.
7. Создать черновик версии; очистить и разделить текст.
8. Проверить фрагменты; пакетно создать и сохранить векторы.
9. Выполнить проверочный поиск только по конкретной версии.
10. **Одной операцией опубликовать новую версию и архивировать прежнюю**.
11. Создать отдельное действие отчёта в Telegram.

Одна задача загрузки на логический документ обрабатывается одновременно. Нумерация версий атомарная; публикация сверяет ожидаемую предыдущую активную версию. Поздно закончившаяся старая задача не может перезаписать новое знание. Конфликт остаётся видимым, не разрешается по времени завершения.

## Проверки и публикация

До публикации:

- непустой набор фрагментов, сохранены все содержательные разделы;
- каждый фрагмент связан с нужной версией и имеет путь, номер, токены и хэш;
- число и размерность векторов совпадают с ожидаемыми;
- контрольные вопросы находят нужные разделы в заданных top-k и пороге;
- ошибки обработки отсутствуют; результаты проверки сохранены с версией;
- документ не изменён другой задачей с момента начала.

Для первой версии документа 3–10 контрольных вопросов задаются автором/Павлом в YAML, сохраняются отдельно в kontrolnye_voprosy и не входят в поисковый текст. Указывается ожидаемый путь раздела; при необходимости — ожидаемый факт. Если вопросов нет, загрузка остаётся ozhidaet_proverki и бот объясняет, что дополнить. Самооценка той же LLM без эталона не считается приёмкой.

У нового документа до публикации может не быть активной версии. У обновляемого — работает старая. Проверочный поиск имеет отдельные права; нельзя открыть черновики клиентскому поиску ради теста.

В одной транзакции публикации проверяется готовность, меняется aktivnaya_versiya_id, новая версия становится opublikovana, прежняя — arhiv, загрузка — zavershena. Нельзя разделить это на независимые n8n-ноды с разными фиксациями.

Ошибка до публикации оставляет старую версию. Сбой Telegram-отчёта после публикации — ошибка уведомления, не отмена или повтор загрузки. Повтор операции публикации возвращает прежний результат.

## Архив, удаление и переиндексация

Старые фрагменты сразу перестают участвовать в клиентском поиске. Физическое удаление выполняется отдельной задачей после срока хранения и проверки зависимостей; массовое удаление активного набора не является частью загрузки.

Отзыв документа из использования — явная административная операция: отключить активную ссылку, сохранить событие; не подменять документ пустым файлом. Возврат из архива требует проверки совместимости модели и качества.

Смена embedding-модели/размерности — отдельная задача переиндексации всего набора компании с тестовым набором и согласованным переключением. Нельзя менять модель одной загрузкой среди старых векторов.
