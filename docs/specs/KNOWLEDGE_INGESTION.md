# Загрузка базы знаний через служебный Telegram-бот

Статус: требования первой версии согласованы. Следующий этап — точная SQL-схема и реализация workflow n8n.

## 1. Цель

Сотрудник компании отправляет Markdown-файл в служебный Telegram-бот. n8n безопасно проверяет, очищает, делит и сохраняет документ в векторное хранилище именно этой компании.

У каждой компании собственные:

- служебный Telegram-бот и токен;
- Telegram Trigger и Credentials;
- служебный workflow;
- schema Supabase;
- список разрешённых Telegram user ID.

Компания не выбирается внутри сообщения. Она заранее закреплена в настройках workflow.

## 2. Входные ограничения

Первая версия принимает только **.md** в UTF-8. Формат описан в [MARKDOWN_FORMAT.md](MARKDOWN_FORMAT.md).

Перед обработкой workflow проверяет:

1. Telegram user ID отправителя;
2. наличие файла;
3. расширение и фактический тип;
4. внутренний лимит размера;
5. возможность прочитать UTF-8;
6. наличие обязательного YAML и одного H1;
7. отсутствие признаков секретов и персональных данных.

Начальный внутренний лимит размера задаётся настройкой внедрения и проверяется на реальных документах. Он не должен молча зависеть только от ограничения Telegram.

## 3. Как определяется новый документ, дубль и обновление

Семантическая похожесть не определяет личность документа.

Workflow рассчитывает:

- SHA-256 исходных байтов;
- SHA-256 нормализованного текста;
- постоянный **identifikator_dokumenta** из YAML.

Решение:

| Ситуация | Действие |
|---|---|
| Идентификатора нет | Отклонить файл и объяснить ошибку |
| Такой hash уже есть | Сообщить «документ уже загружен», ничего не менять |
| Идентификатор новый | Создать первый вариант документа |
| Идентификатор есть, hash изменился | Создать новую версию |
| Текст похож, но идентификатор другой | Не заменять автоматически; при необходимости показать предупреждение |

Имя файла хранится для удобства, но не является постоянным ключом.

## 4. Очистка текста

Очистка не должна пересказывать текст или изменять факты.

Разрешено:

- нормализовать UTF-8, переводы строк и пробелы;
- убрать YAML из поискового текста, сохранив поля в metadata;
- убрать HTML-комментарии, script/style и технический мусор;
- убрать пустые декоративные разделители;
- сократить повторяющиеся пустые строки;
- убрать полностью одинаковые повторяющиеся блоки;
- привести заголовки к проверенной иерархии;
- сохранить порядок текста, списки, таблицы, единицы и артикулы.

Запрещено автоматически «улучшать» характеристики, цены, гарантии и условия с помощью модели. Если структура нарушена неоднозначно, файл отклоняется с понятным сообщением.

## 5. Деление на фрагменты

Основное правило: сначала структура Markdown, затем размер.

Каждый фрагмент получает путь заголовков, например:

**Пластиковые окна > Характеристики > Модель Alfa 70**

Стартовые параметры для тестирования, а не универсальный стандарт:

- целевой размер: 400–700 токенов;
- жёсткий максимум: 800 токенов;
- перекрытие: 80–120 токенов только при разрезании длинного раздела;
- слишком маленький раздел объединяется с соседним внутри того же родительского раздела.

Разрез выполняется по абзацам или предложениям. По возможности нельзя разделять:

- вопрос и ответ;
- строку таблицы и её заголовки;
- один список характеристик;
- описание одной модели;
- кодовый блок.

Специальные правила:

- FAQ: один вопрос с ответом — один фрагмент;
- характеристики: одна модель или товарная группа — один или несколько связанных фрагментов;
- таблица: заголовок таблицы повторяется для каждой группы строк;
- длинный раздел: каждый фрагмент получает его путь заголовков.

Для каждого фрагмента сохраняются номер, путь раздела, количество токенов, hash, тип документа, версия и модель embedding.

## 6. Создание embeddings

- Все сравниваемые фрагменты создаются одной моделью embedding и с одной размерностью.
- Название модели и размерность сохраняются вместе с версией документа.
- Смена модели требует отдельной полной переиндексации; старые и новые векторы не смешиваются.
- Обработка выполняется пакетами с ограниченным числом повторных попыток.
- Ошибка любого обязательного фрагмента оставляет новую версию неактивной.
- Для поиска стартово используется cosine distance.
- Порог сходства и число результатов определяются тестами на реальных вопросах компании.
- Для артикулов и точных терминов в будущем следует добавить гибридный поиск: векторный плюс полнотекстовый.

## 7. Безопасное обновление

Нельзя сначала удалить рабочие данные, а потом создавать новые.

Порядок:

1. Создать новую версию со статусом **poluchen**.
2. Проверить и подготовить все фрагменты.
3. Создать все embeddings.
4. Сохранить новую версию как неактивную.
5. Выполнить проверки качества.
6. Одной транзакцией сделать новую версию активной и старую архивной.
7. Физическое удаление старых фрагментов выполнять позднее по отдельному правилу хранения.

Так выполняется требование замены данных без риска остановить поиск. Клиентский бот всегда видит только активную версию. При ошибке старая версия продолжает работать.

## 8. Проверка качества до публикации

Обязательно проверить:

- создан хотя бы один непустой фрагмент;
- число embeddings равно числу фрагментов;
- у каждого фрагмента есть документ, версия и путь раздела;
- нет неожиданных полных дублей;
- размер фрагментов находится в допустимых пределах;
- поиск по контрольным вопросам возвращает ожидаемые разделы;
- активной остаётся ровно одна версия идентификатора;
- запрос из другой schema не получает эти данные.

Для первой проверки документа используется 3–10 контрольных вопросов. Набор вопросов хранится отдельно от документа и повторно используется после изменений чанкинга или модели.

## 9. Логика workflow n8n

Рекомендуемые ноды:

1. **Телеграм — Получен документ**
2. **Проверить отправителя**
3. **Проверить формат файла**
4. **Скачать документ**
5. **Рассчитать SHA-256**
6. **Разобрать Markdown**
7. **Проверить обязательные поля**
8. **Найти документ по идентификатору и хэшу**
9. **Очистить текст**
10. **Разделить на фрагменты**
11. **Проверить фрагменты**
12. **Создать embeddings**
13. **Сохранить новую версию**
14. **Проверить поиск**
15. **Опубликовать новую версию**
16. **Архивировать старую версию**
17. **Отправить отчёт**

Ветка ошибки записывает **sistemnye_sobytiya**, меняет статус новой версии на **oshibka**, не трогает активную версию и отправляет уведомление.

## 10. Ответ служебного бота

Успешная загрузка сообщает:

- название и идентификатор;
- результат: новый, дубль или обновление;
- номер версии;
- количество разделов и фрагментов;
- дату публикации;
- предупреждения.

Ошибка сообщает этап, простую причину и действие пользователя. Секреты, полный stack trace и service role в Telegram не отправляются.

## 11. Защита данных компании

- Клиентский и служебный workflow используют фиксированную schema.
- Schema не берётся из Telegram, файла или запроса клиента.
- Таблицы базы знаний находятся в schema компании.
- SQL-функция поиска ограничивает выборку активными фрагментами этой schema.
- service role доступен только серверному процессу.
- Дашборд работает через ограниченный серверный API или RLS.
- Перед внедрением выполняются положительные и отрицательные тесты доступа.

## 12. Основания для решений

- [Supabase: Vector columns](https://supabase.com/docs/guides/ai/vector-columns) — pgvector, размерность, операторы и необходимость одной модели.
- [Supabase: Semantic search](https://supabase.com/docs/guides/ai/semantic-search) — embeddings и фильтрация внутри SQL-поиска.
- [Supabase: Custom schemas](https://supabase.com/docs/guides/api/using-custom-schemas) — отдельные schema и явное предоставление доступа.
- [Supabase: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security) — RLS и запрет использования service role в клиенте.
- [OpenAI Cookbook: Embedding long inputs](https://developers.openai.com/cookbook/examples/embedding_long_inputs) — длинные тексты нужно сокращать или делить; деление по смысловым границам сохраняет контекст.
- [n8n: Telegram Trigger](https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.telegramtrigger/) — получение сообщений и файлов, фильтрация Chat ID/User ID.
- [n8n: Telegram node](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/) — скачивание файла и отправка отчёта.

Числа для размера фрагментов и перекрытия являются стартовой инженерной настройкой проекта. Они должны быть подтверждены контрольными вопросами, а не восприниматься как правило конкретного сервиса.
