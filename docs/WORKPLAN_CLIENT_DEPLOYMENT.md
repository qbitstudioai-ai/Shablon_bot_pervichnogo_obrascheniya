# План копирования и внедрения для компании

Используется после готовности версии шаблона REL-01. Скопируй этот план и [паспорт](../templates/company-passport.md) в закрытую документацию внедрения. Чекбоксы разных компаний не ведутся в одном общем экземпляре.

В публичном репозитории остаются общие шаблоны. Реальные документы, токены, переписка и частные сведения компании сюда не добавляются.

Внедрение проходит на том же серверном Supabase: новые schema и ограниченные роли, без создания облачного проекта. Структура БД устанавливается готовыми миграциями; Павел не пишет SQL.

## Последовательность

Каждая строка — результат отдельной сессии. Крупную строку ChatGPT заранее делит на подзадачи с ID. Частный PROJECT_STATE указывает компанию, среду и один следующий ID.

| Статус / ID | Зависимость | Результат и проверка |
|---|---|---|

| [ ] DEP-02 | DEP-01 | Проверена совместимость сервера и создана тестовая schema с ролями; положительные и отрицательные проверки доступа пройдены |

| [ ] DEP-04 | DEP-03 | Подключены отдельные тестовые клиентский и служебный боты; доверенный источник и разрешённый служебный отправитель проверены |
| [ ] DEP-05 | DEP-04 | Знания загружены служебным ботом; контрольные вопросы, точный дубль, обновление и ошибка обновления пройдены |

Если производство уже обслуживает клиентов, подготовка DEP-09 не останавливает существующий путь до согласованного переключения. SQL и действия предоставляются полностью, с короткой инструкцией и проверкой.

## Что заполняется при обычном внедрении

Паспорт собирает сведения один раз. Из него заполняются блок n8n «МЕНЯТЬ ПРИ ВНЕДРЕНИИ», Credentials и оформление дашборда:

- код компании, schema/среда, ограниченные подключения;
- название, контакты, регион, предложение, часовой пояс бизнеса;
- клиентские каналы и отдельный служебный бот;
- разрешённые Telegram user ID/chat ID Павла;
- режим CRM: net, bitrix24 или amocrm; маршрут заявки и передача сотруднику;
- prompts и проверенные параметры LLM/поиска, профиль индекса;
- логотип, оформление и доступы дашборда.

CORE и миграции вручную под компанию не переписываются. Если требуется новое поведение, создаётся отдельная задача шаблона с проверкой совместимости существующих установок.

## Telegram: служебный бот, test и prod

У каждой компании свой служебный бот со своим токеном. Его workflow принимает документы и отправляет Павлу уведомления.

Это **не устраняет** ограничение одного webhook на токен. Клиентский и служебный боты различаются между собой; для test и prod также используются разные токены. Если клиентский канал Telegram подключён в обеих средах, это четыре разных бота: клиентский test/prod и служебный test/prod.

Не включай Listen for test event с рабочим токеном. Не оставляй активными старый и новый получатель одного токена. Проверка отключённого n8n выполняется внешним мониторингом, который может отправить уведомление напрямую без нового входящего Telegram Trigger.

## Выпуск и откат

До переключения известны предыдущая рабочая версия, резервная копия, порядок возвращения трафика и условия остановки. Импорт JSON, привязка Credentials и активация — отдельные шаги с отдельным подтверждением результата.

При серьёзной ошибке приостанавливается только затронутая компания, если это технически возможно. Входящие не отбрасываются: используется проверенный приём/буфер. Не возвращай старый код поверх несовместимой БД и не восстанавливай всю общую БД, затирая новые данные других компаний.

После запуска в частном паспорте фиксируются фактические версии и время применения. Значение «файл есть на GitHub» не заменяет эти сведения.

## Следующие обновления компании

Отдельная задача: сравнить версию компании с эталоном → проверить миграции и совместимость → применить на test → пройти затронутые проверки → подготовить откат → получить разрешение рабочего переключения → обновить prod → проверить и записать результат.

Изменённый компанией логотип или конфигурация не затираются обновлением CORE. Тестовые сообщения и учебные документы в рабочую аналитику и знания не переносятся.
