# План 2. Внедрение шаблона в новую компанию

## Назначение

Этот план используется только после появления проверенной версии TEMPLATE.

Рекомендация: каждое клиентское внедрение хранить в отдельном приватном GitHub-репозитории. Репозиторий шаблона публичный, поэтому в нём нельзя хранить клиентские данные, индивидуальные prompts, внутренние документы или настройки.

Секреты не сохраняются ни в одном GitHub-репозитории.

## Этап 1. Подготовка

- [ ] Выбрать стабильную версию TEMPLATE и записать её Git-тег или commit SHA.
- [ ] Создать отдельный приватный репозиторий компании.
- [ ] Скопировать в него выбранную версию шаблона.
- [ ] Зафиксировать кодовое имя компании без персональных и секретных данных.
- [ ] Создать клиентский `PROJECT_STATE.md`.
- [ ] Определить ответственных и безопасный способ обмена доступами.

Результат этапа: создана изолированная рабочая копия с известной исходной версией.

## Этап 2. Обследование компании

- [ ] Описать каналы обращений.
- [ ] Описать реальный путь клиента.
- [ ] Определить цели бота.
- [ ] Определить обязательные вопросы и данные.
- [ ] Определить, что считается квалифицированным обращением.
- [ ] Определить условия передачи человеку.
- [ ] Определить CRM и необходимые поля.
- [ ] Определить базу знаний.
- [ ] Определить отчёты и метрики.
- [ ] Зафиксировать индивидуальные требования и границы внедрения.

Результат этапа: понятно, какие части шаблона включаются и какие значения меняются.

## Этап 3. Supabase

- [ ] Создать schema компании готовым SQL-шаблоном.
- [ ] Проверить структуру schema.
- [ ] Настроить необходимые права доступа.
- [ ] Загрузить безопасные тестовые данные.
- [ ] Подготовить и загрузить базу знаний.
- [ ] Проверить векторный поиск.
- [ ] Проверить запись и чтение данных.
- [ ] Удалить тестовые данные перед production, если требуется.

Результат этапа: изолированное хранилище компании готово к работе.

## Этап 4. n8n

- [ ] Скопировать эталонный workflow.
- [ ] Переименовать workflow по стандарту.
- [ ] Указать версию TEMPLATE в заметке workflow.
- [ ] Изменить только блок «МЕНЯТЬ ПРИ ВНЕДРЕНИИ».
- [ ] Подключить нужные каналы.
- [ ] Подключить n8n Credentials.
- [ ] Указать schema и таблицы Supabase.
- [ ] Указать базу знаний.
- [ ] Настроить prompts.
- [ ] Выбрать CRM через маршрутизатор.
- [ ] Настроить необходимые бизнес-параметры.
- [ ] Убедиться, что CORE не изменён без отдельного решения.
- [ ] Экспортировать безопасный JSON без секретов в приватный репозиторий.

Результат этапа: создан рабочий экземпляр workflow компании.

## Этап 5. Дашборд

Исполнитель разработки и деплоя: VSCode. Руководитель и проверяющий: ChatGPT.

- [ ] Скопировать стабильную версию шаблона дашборда.
- [ ] Настроить подключение к schema компании через переменные окружения.
- [ ] Указать название, логотип и домен.
- [ ] Включить согласованные отчёты и метрики.
- [ ] Настроить авторизацию и доступ.
- [ ] Выполнить локальные тесты.
- [ ] Выполнить тестовое развёртывание.
- [ ] Проверить данные и фильтры вместе с Павлом.
- [ ] Выполнить production-деплой после согласия Павла.

Результат этапа: руководство компании видит только свои данные и согласованные отчёты.

## Этап 6. Проверка до запуска

- [ ] Проверить каждый входной канал.
- [ ] Проверить ответ в тот же канал и диалог.
- [ ] Проверить обычные обращения.
- [ ] Проверить неизвестные и неполные обращения.
- [ ] Проверить работу базы знаний.
- [ ] Проверить передачу человеку.
- [ ] Проверить CRM и соответствие полей.
- [ ] Проверить Supabase и отчёты.
- [ ] Проверить защиту от дублей.
- [ ] Проверить восстановление после ошибок.
- [ ] Проверить отсутствие секретов в GitHub и экспортируемом JSON.
- [ ] Получить подтверждение Павла на запуск.

Результат этапа: выполнены критерии приёмки и получено разрешение на production.

## Этап 7. Запуск

- [ ] Создать резервные копии и точку возврата.
- [ ] Активировать production-workflow.
- [ ] Выполнить контрольное обращение.
- [ ] Проверить n8n, Supabase, CRM и дашборд.
- [ ] Зафиксировать дату запуска и версии компонентов.
- [ ] Зафиксировать известные ограничения.
- [ ] Подготовить краткую инструкцию эксплуатации.
- [ ] Определить порядок уведомления об ошибках.

Результат этапа: экземпляр компании работает и имеет понятную точку восстановления.

## Этап 8. Сопровождение

- [ ] Вести журнал индивидуальных отклонений от TEMPLATE.
- [ ] Не изменять CORE без отдельного анализа.
- [ ] Проверять обновления TEMPLATE на применимость.
- [ ] Переносить исправления сначала в тестовую копию.
- [ ] Повторять критические тесты перед production.
- [ ] Обновлять клиентский план и `PROJECT_STATE.md`.
- [ ] Фиксировать версию после каждого production-изменения.

Результат этапа: клиентская версия остаётся управляемой и не теряет связь с шаблоном.
