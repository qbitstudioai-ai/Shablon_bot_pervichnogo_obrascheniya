# Правила документации

## Цель

Новая сессия ChatGPT и VSCode должны понимать смысл решения без доступа к истории разговоров. При этом документация не должна дублировать сама себя.

## Уровни

### 1. Обзор

`README.md` отвечает на вопросы:

- что строим;
- какие основные принципы;
- где находится подробная документация.

### 2. Управление работой

- `docs/PROJECT_STATE.md` — текущее состояние и один следующий блок;
- `docs/WORKPLAN_TEMPLATE.md` — создание шаблона;
- `docs/WORKPLAN_CLIENT_DEPLOYMENT.md` — внедрение компании.

### 3. Архитектура и спецификации

- `docs/ARCHITECTURE.md` — связь компонентов;
- `docs/DATA_DICTIONARY.md` — смысл данных;
- `docs/specs/` — точные правила отдельных механизмов.

## Правило одного источника

Каждое правило подробно описывается только в одном файле.

Другие документы дают короткое резюме и ссылку. При изменении обновляется основной документ и все устаревшие краткие утверждения.

## Структура спецификации

Каждая спецификация по возможности содержит:

1. назначение;
2. простое объяснение;
3. термины;
4. бизнес-правила;
5. входные данные;
6. результат;
7. исключения и ошибки;
8. данные, которые сохраняются;
9. проверки готовности;
10. открытые решения.

Раздел добавляется только если он действительно нужен.

## Статус информации

Используются ясные формулировки:

- **согласовано** — решение принято;
- **предварительно** — рабочее направление;
- **открытый вопрос** — решение ещё не принято;
- **проверено** — есть результат теста;
- **не проверено** — реализация или тест отсутствуют.

Предположение нельзя записывать как готовую возможность системы.

## Планы

Название пункта должно описывать проверяемый результат, а не абстрактное действие.

Плохо:

```text
Сделать RAG
```

Хорошо:

```text
Загрузить тестовый Markdown, создать чанки и подтвердить,
что поиск возвращает нужный фрагмент по контрольному вопросу
```

Пункт отмечается `[x]` только после указанной проверки.

## PROJECT_STATE

После законченного блока фиксируются:

- что выполнено;
- принятое решение;
- как проверено;
- commit SHA при наличии;
- блокеры;
- один следующий блок.

Файл не превращается в полный журнал. Устаревшие подробности остаются в Git-истории и спецификациях.

## Примеры и пояснения

Пример добавляется, когда без него термин может пониматься по-разному. Один хороший пример лучше нескольких повторяющихся объяснений.

## Код и документация

- изменение поведения требует обновления соответствующей спецификации;
- VSCode обновляет относящиеся к задаче документы в том же commit;
- ручное изменение n8n считается завершённым после подтверждения Павла и сохранения безопасного JSON;
- секреты, реальные токены и клиентские персональные данные в документацию не попадают.
