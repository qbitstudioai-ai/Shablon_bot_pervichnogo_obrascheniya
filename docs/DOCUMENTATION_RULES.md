# Правила документации

Цель: новая сессия должна продолжить одну задачу без старой переписки. Подробное правило имеет один основной документ; в остальных местах — короткое резюме и ссылка.

## Как записывать требования

У правила должны быть понятны причина, действие, входные данные, результат и важные исключения. Добавляй пример там, где он снимает неоднозначность. Термин объясняй при первом использовании: например, «атомарно — все изменения сохраняются вместе либо не сохраняется ни одно».

Различай:

- **Требование** — так должна работать будущая система.
- **Принятое решение** — выбранный способ выполнения требования.
- **Параметр внедрения** — значение выбирается для установки и записывается в паспорт.
- **Создано в файлах** — результат существует в репозитории.
- **Применено** — есть подтверждение изменения конкретной среды.
- **Проверено** — указан сценарий, среда, версия и фактический результат.

Фраза «в документации предусмотрена изоляция» не означает, что права уже созданы. Возможность продукта сверяй с официальной документацией выбранной версии. Записывай источник и дату проверки; отсутствие доступа к серверу не заменяй предположением о его настройках.

## Как вносить изменения без потери требований

1. Прочитай текущую версию основного документа и связанные краткие утверждения.
2. Сопоставь изменение с исходным требованием Павла. Не удаляй требование только потому, что реализация ещё не выбрана.
3. Обнови основной документ, связанные контракты/данные, критерии проверки и затронутые резюме.
4. Проверь относительные ссылки, примеры дат, одинаковые названия состояний, зависимости задач и отсутствие секретов.
5. Просмотри различия: каждое удаление должно быть объяснимо. Старые тексты сохраняет Git; отдельные противоречащие «финальные версии» не создаются.
6. Обнови состояние и план той же задачей. Сохрани понятный commit.

Новые решения могут заменять старые. Актуальное правило явно фиксируется в основном документе; сам факт наличия старого commit не делает прежнее поведение действующим.

## Учёт задач и доказательств

Постоянный ID задачи не переиспользуется. Статусы: `[ ]` не начато, `[~]` в работе, `[x]` проверено и завершено, `[!]` пауза с причиной.

Если крупный пункт не помещается в одну сессию, перед началом раздели его на ID вида `DB-01.1`, `DB-01.2` с отдельными критериями. Родитель готов только после обязательных подзадач.

Для закрытия задачи нужны результат и её критерий приёмки. Документационная задача закрывается проверкой документов; рабочая — проверкой реализации. Отчёт сохраняет также то, что не проверялось.

После ручного импорта Павлом запиши среду, версию файла, время и результат. Файл JSON в GitHub не доказывает, что он импортирован или включён в n8n. Если результат содержит личные данные, в публичном репозитории остаётся только обезличенное подтверждение; подробности хранятся в закрытом журнале установки.

## GitHub и локальная копия

До изменения проверь ветку, исходный SHA и несохранённые правки. Один исполнитель владеет текущей задачей. Перед push учти новые изменения в удалённой ветке; конфликты разрешаются по смыслу, без принудительной перезаписи.

Код и документация задачи сохраняются вместе, если возможно. Для ручного действия документация обновляется сразу после подтверждения. Если push или доступ к GitHub не сработал, статус «не опубликовано» явно остаётся в передаче; нельзя советовать новому чату искать несуществующий commit.

Текущий commit не записывают внутрь самого себя: PROJECT_STATE называет ID задачи и файлы, а окончательный SHA — в сообщении передачи или в последующем журнале. Новый чат проверяет актуальную вершину ветки.

## Публичность и объём

В этот репозиторий попадают шаблоны, безопасные примеры и общие решения. Частные паспорта компаний, клиентские документы, чаты, секреты и резервные копии хранятся вне публичного репозитория.

PROJECT_STATE остаётся коротким. Полная история — в Git. Не копируй все спецификации в каждое сообщение передачи: достаточно ID задачи, точных ссылок и подтверждений.
