## Следующая одна задача

**PRE-01 — проверить фактический паспорт сервера и выбрать реализуемый путь первого канала. Статус: завершено.**

Нужно подтвердить реальные версии и режимы n8n, Supabase/PostgreSQL/pgvector, доступные механизмы Auth и подключения, а также способ надёжного приёма Telegram до окончательного подтверждения webhook.

PRE-01 начат 23 сентября 2026 года. Подтверждены версии Docker, n8n, Supabase/PostgreSQL, Auth, Supavisor и основных контейнеров. Supabase развёрнут через Docker; n8n использует отдельный контейнер PostgreSQL. pgvector 0.8.2 активирован и функционально проверен. Павел разрешил подготовить Supabase как рабочую платформу для шаблона. `vector` уже включён и проверен. Инвентаризация расширений показала: установлены `vector 0.8.2`, `pgcrypto 1.3`, `pg_stat_statements 1.11`, `pg_net 0.20.3`, `uuid-ossp 1.1`; доступны, но не установлены `pg_trgm`, `unaccent`, `pgmq`, `pg_cron`, `postgis`, `pgaudit`, `pg_graphql`, `citext`, `ltree`. Дополнительные расширения включаются только под конкретную задачу. Также официально подтверждено: self-hosted Supabase работает как один project, Studio не поддерживает несколько organizations/projects; изоляция компаний остаётся через schema и ограниченные роли. Сетевая проверка показала: `n8n` подключён к Docker-сетям `net-data` и `net-edge`, а `supabase-db` и `supabase-pooler` — к `supabase_default`; из n8n порты `supabase-db:5432`, `supabase-pooler:5432` и `:6543` недоступны (TIMEOUT). PostgreSQL наружу не опубликован; Supavisor опубликован только на loopback `127.0.0.1`. Compose-файлы найдены: n8n — `/opt/katona/n8n/docker-compose.yml`; Supabase — `/opt/katona/supabase/src/docker/docker-compose.yml` плюс override `/opt/katona/supabase/src/docker/docker-compose.katona.yml`. `n8n` использует сервисы `n8n-db`, `n8n` и сети `net-data`, `net-edge`; Supabase использует сервисы `db`, `studio`, `api-gw`, `functions`, `meta`, `rest`, `imgproxy`, `storage`, `supavisor`, `auth`, `realtime` и сети `default`, `net-edge`. Сеть `net-edge` уже общая для двух Compose-проектов, но `supabase-db` к ней не подключён; база остаётся только в `supabase_default`. Выбрано решение подготовить отдельную минимальную сеть связи только между `n8n` и `supabase-db`, не расширяя доступ БД на `net-edge` и не публикуя порт 5432 наружу. После проверки соединения перейти к ограничениям Telegram. Workflow в PRE-01 не проектируется. Перед началом последующего проектирования n8n необходимо отдельно запросить у Павла обещанный эталонный образец и изучить его.

Закрытая связь n8n и Supabase PostgreSQL настроена 23 сентября 2026 года с отдельного разрешения Павла. Создана постоянная Docker bridge-сеть `qbit-db-link` (driver `bridge`, подсеть 172.22.0.0/16), объявленная как external в обоих Compose-проектах. Изменены два серверных файла: `/opt/katona/n8n/docker-compose.yml` — сервису `n8n` добавлена сеть `qbit-db-link`, сервис `n8n-db` не менялся; `/opt/katona/supabase/src/docker/docker-compose.katona.yml` — сервису `db` явно заданы сети `default` и `qbit-db-link` с алиасом `supabase-db`, добавлено объявление внешней сети. Upstream-файл `/opt/katona/supabase/src/docker/docker-compose.yml` не изменялся. Перед изменением сделаны резервные копии с меткой `20260923-082452`. `net-edge` для этой связи не используется; существующие сети `net-edge`, `net-data`, `supabase_default` сохранены без изменений.

К сети `qbit-db-link` подключены ровно два контейнера: `n8n` (172.22.0.2) и `supabase-db` (172.22.0.3). Caddy, Envoy, Studio, Auth, Storage, Rest, Realtime, imgproxy, meta, Supavisor и `n8n-db` к ней не подключены. Проверка из контейнера n8n: `supabase-db:5432` — OK, соединение установлено с 172.22.0.3, сервер ответил на PostgreSQL SSLRequest. `n8n-db:5432` — OK через `net-data` (172.19.0.2), то есть базы n8n и Supabase не перепутаны. `supabase-pooler:5432` и `:6543` из n8n по-прежнему недоступны; изменение Supavisor в задачу не входило. Связь сохраняется после `docker compose up -d` и после `docker restart` обоих контейнеров; повторный `docker compose up -d --dry-run` не пересоздаёт `n8n` и `supabase-db`. Все контейнеры остались в состоянии running, контейнеры с healthcheck — healthy.

PostgreSQL наружу не опубликован. У `supabase-db` host-порт отсутствует; единственный контейнер с привязкой к 0.0.0.0 — Caddy (80/443); Supavisor опубликован только на `127.0.0.1:5432` и `127.0.0.1:6543`. Подключение к публичному адресу сервера на порт 5432 с самого сервера завершается `Connection refused` при неактивном UFW, то есть закрытость обеспечена привязкой, а не firewall. Публикация `5432:5432` не добавлялась, порты, volumes и переменные окружения не менялись, `docker compose down -v` не выполнялся, данные и volumes не удалялись. Базы данных, таблицы, schema, роли PostgreSQL и данные в этой задаче не изменялись; workflow n8n не проектировался и не изменялся.

Веб-интерфейсы после изменения работают как до него: `https://n8n.qbit-product.ru/` отвечает 200, `https://n8n.qbit-product.ru/healthz` возвращает `{"status":"ok"}`; Supabase Studio и `/rest/v1` отвечают 401 — это требование basic-аутентификации шлюза, то же поведение было зафиксировано до изменения.

Не проверено: сохранение связи после перезагрузки сервера — сервер не перезагружался; подключение к PostgreSQL Supabase с учётными данными — Credentials в PRE-01 не настраивались; внешняя проверка закрытости порта 5432 с рабочей станции признана недостоверной, поскольку сеть рабочей станции устанавливает TCP-соединение с любым портом сервера, включая заведомо неиспользуемый, поэтому вывод сделан по данным сервера. Отдельно зафиксировано ранее существовавшее расхождение: `docker compose up -d` в проекте Supabase пересоздал бы `supabase-storage` и `supabase-edge-functions`; расхождение появилось до этой задачи, к `qbit-db-link` отношения не имеет и не устранялось.

Проверка отчёта по commit `6e1ffc96102ba8f273c022776092144f1eb413fc` подтверждена чтением GitHub: сетевой подэтап PRE-01 выполнен. Отдельная сеть `qbit-db-link` обеспечивает доступ `n8n -> supabase-db:5432`, PostgreSQL наружу не опубликован. PRE-01 целиком ещё не завершён: для Telegram подтверждено по исходнику n8n 2.41.0, что встроенный `Telegram Trigger` регистрирует webhook с `secret_token`, работает с `responseMode: onReceived` и для версии узла >=1.3 задаёт `drop_pending_updates=true`. Это не доказывает требуемый порядок «сначала долговечная запись входа в Supabase, затем HTTP 2xx» и может удалять накопившиеся pending updates при перерегистрации webhook. До выбора входного решения встроенный Trigger не считать надёжным приёмником production.

Павел передал внешний пример `ZONT Support AI — Telegram RAG v5.2`; он изучен как источник архитектурных приёмов, а не как эталон или готовый импорт. Сильные идеи — атомарный план поиска, multi-query RAG, evidence, строгий JSON и проверка источников. Не переносим: ранний Telegram Trigger, прямой Supabase Data API к schema, исходный текст в внешние AI, память одного последнего вопроса, порог vector search 0, жёстко пришитые модели/URL/ID и отправку до регистрации исходящего действия.

PRE-01 закрыт выбором реализуемого Telegram-пути: Webhook node n8n 2.41.0 с Header Auth по `X-Telegram-Bot-Api-Secret-Token`, транзакционная запись входного события/сообщения/задания через ограниченное PostgreSQL-подключение и Respond to Webhook 200 только после commit. Telegram при non-2xx повторяет webhook; `drop_pending_updates` в обычной регистрации не включается. Долгая обработка идёт из долговечной очереди после подтверждения, а RT-01 позже проверит отключение БД, дубли, перезапуск и восстановление на тестовом боте.

Создана спецификация `docs/specs/BOT_CORE_WORKFLOW.md`: явный CORE вместо привилегированного AI Agent, локальная очистка PII до LLM/embeddings, память 3–5 сообщений плюс долговечные факты, тематический guard, три предупреждения и логическая блокировка, ручной перехват менеджером, grounded RAG и настраиваемые сценарии. Для qBit стартовые напоминания изменены на 3 часа и 12 часов; шаблон хранит интервалы как настройки. Исполняемый workflow, SQL и production Telegram не менялись.

## Следующая одна задача

**PRE-02 — зафиксировать профиль обработки. Статус: в работе.**

Павел выбрал семейство Qwen вместо OpenAI, так как OpenAI API не рассматривается для российского сервера. Для первого проверяемого профиля выбран Alibaba Cloud Model Studio с pay-as-you-go. Регион внешнего Qwen API пока не выбран: сравниваются Singapore и China (Beijing) по возможности регистрации/оплаты, доступности нужных моделей и фактической связности/задержке с российского сервера. Географическое положение Павла не используется при выборе архитектуры; вся основная инфраструктура проекта остаётся на российском сервере. Месячные Token/Coding Plans не используются для backend-бота; резервирование throughput рассматривается только после измерения нагрузки. В n8n 2.41.0 подтверждена штатная нода `Qwen Cloud Chat Model` с Credential `Qwen Cloud`; для embeddings отдельной Alibaba-ноды в этой версии не найдено, поэтому embedding adapter будет проверяться через OpenAI-compatible API/HTTP Request. Планируется два отдельных API key в одном workspace с минимальными правами: LLM и embeddings. Секреты в GitHub не сохраняются.

Следующий шаг PRE-02 — подтвердить подходящий регион Alibaba Cloud для российского сервера, затем Павел создаёт/активирует Model Studio и два ограниченных API key без передачи ключей в чат; после этого проверяется реальная доступность API с российского сервера и из n8n. После этого фиксируются конкретные модели, размерность, tokenizer, parser, лимиты, top-k/порог и контрольный набор.

До PRE-02 не создаём рабочий клиентский workflow.
