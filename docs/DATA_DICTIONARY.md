# Словарь данных

Описательная модель v0.3 для одной schema компании. Точные типы, обязательность, индексы, роли и атомарные PostgreSQL-функции зафиксированы в [DB_CONTRACT.md](specs/DB_CONTRACT.md). SQL и миграции создаются следующими задачами DB-01…DB-05; перечисленные связи и смысл обязательны для реализации.

## Общие правила

- Все таблицы компании находятся в её schema; повторять доступ к чужим schema через общий ключ нельзя.
- ID — внутренние UUID, внешние ID — строки. Даты событий и записи различаются и сохраняют часовой пояс/UTC.
- Исходный текст неизменяем; правка сообщения — отдельное событие/редакция.
- История этапов, целей, потерь, возвратов и административных действий дополняется.
- Структура одинакова у всех компаний; индивидуальные таблицы при обычном копировании не создаются.
- Секреты, Credentials и произвольные исполняемые prompts в этих таблицах не хранятся.

Уникальность идентичности — канал + аккаунт + внешний пользователь внутри schema. Уникальность внешнего сообщения учитывает аккаунт/диалог. Поле первого обращения не обновляется при возврате.

Этапы и статусы определены в [CONVERSATION_LIFECYCLE.md](specs/CONVERSATION_LIFECYCLE.md). Сырые контакты/сообщения имеют отдельные права колонок или закрытые представления; право читать метрики не даёт автоматически право читать весь исходный текст.

| menedzhery_telegram | внутренний ID менеджера; разрешённый Telegram user_id, подтверждённый private chat_id после /start, отображаемое имя, активность/право захвата; без bot token |
| sobytiya_zerkala_operatora | id, dialog_id, soobshchenie_id при наличии; tip_sobytiya, ключ идемпотентности, статус, число попыток, следующий запуск, внешний message ID, безопасная ошибка |

Операторская тема и зеркало не заменяют архив сообщений: Telegram-группа является рабочим представлением, а Supabase остаётся источником истины.

Исходящее действие и сообщение — связанные, но разные сущности: одна запись описывает попытки отправки, другая — реплику диалога. Повтор попытки не создаёт новое логическое сообщение. Отдельная строка памяти не заменяет архив.

Система определяет пользователя отчёта по событиям, не по сумме диалогов; правила находятся в [METRICS.md](specs/METRICS.md).

## База знаний

| Таблица | Поля и назначение |
|---|---|
| zagruzki_znaniy | id; ID зарегистрированного служебного события Telegram, отправитель/чат/file_id, имя файла; ishodnyy_fayl (исходные байты), размер, hash_istochnika/hash_soderzhaniya; время/порядок приёма; status, код ошибки, документ/версия при наличии |
| zadaniya_znaniy | id, zagruzka_id, dokument_id; тип/status, приоритет/попытки/следующий запуск, владелец/срок аренды/номер владения, ожидаемая активная версия и безопасная payload/error. Обеспечивает долговечную последовательную очередь одного логического документа |
| dokumenty_znaniy | id; уникальный identifikator_dokumenta; aktivnaya_versiya_id (может быть пустым до публикации или после отзыва); время создания |
| versii_dokumentov_znaniy | id, dokument_id, zagruzka_id; nomer_versii, nazvanie, tip_dokumenta, versiya_istochnika, data_obnovleniya; hash_soderzhaniya, otpechatok_obrabotki, profil_indeksa_id; status; время проверки/публикации/архивирования; ожидаемая предыдущая версия |
| fragmenty_znaniy | id, versiya_id; nomer_fragmenta, put_razdela; tekst_fragmenta (точный текст для embedding с заголовками), kolichestvo_tokenov, hash_fragmenta, vektor; время создания |
| profili_indeksa | id; модель/размерность embedding, версия parser/очистки/чанкинга, размеры и токенизатор; неизменяемый снимок параметров из n8n для воспроизводимости |
| kontrolnye_voprosy | id, versiya_id; vopros, ozhidaemyy_razdel, ozhidaemyy_fakt при наличии; источник эталона |
| proverki_znaniy | id, versiya_id, vopros_id; профиль/порог/лимит поиска, полученные ID фрагментов, результат проверки, время/ошибка |

Один документ — много версий; одна версия — много фрагментов. Только aktivnaya_versiya_id определяет клиентскую видимость. Ссылка обязана вести на опубликованную версию того же документа; это проверяется БД.

Уникальны dokument_id + nomer_versii и versiya_id + nomer_fragmenta. Одинаковый текст в разных разделах допускается. Нет уникальности по паре «документ + false» и нет независимого aktiven у каждого фрагмента.

## Точный DB-контракт

[DB_CONTRACT.md](specs/DB_CONTRACT.md) фиксирует для DB-01…DB-05 полный список полей, типов, индексов, ролей и функций, а также проверки идемпотентности, очередей, операторского Telegram и публикации знаний. Будущий SQL реализует этот контракт и не может молча удалить поле или поменять бизнес-смысл.

Сроки очистки и хранения остаются PRE-03; представления отчётов — задачами UI. Связи и форматы операций: [INTEGRATION_CONTRACTS.md](specs/INTEGRATION_CONTRACTS.md). Доступ: [ACCESS_AND_ISOLATION.md](specs/ACCESS_AND_ISOLATION.md). DB-01 и DB-02 уже применены в test-контуре: созданы test schema/роли и 13 таблиц пользовательского/диалогового слоя. DB-03 разбит на DB-03A…DB-03D; DB-03A и DB-03B успешно применены и проверены в test-контуре. Родительский DB-03C дополнительно разделён на DB-03C1…C4. DB-03C1 v0.3 успешно применён и проверен; DB-03C2 ещё не применён.
