# Словарь данных Supabase

## Назначение

Документ объясняет простым языком, какие группы данных нужны и для чего. Это ещё не SQL-схема: точные названия, типы и ограничения будут утверждены перед созданием миграции.

## Общие правила

- одна компания — одна schema;
- структура schema одинакова у всех компаний;
- все даты хранятся с часовым поясом;
- внешние события имеют уникальный идентификатор для защиты от дублей;
- исходный и обезличенный текст разделяются;
- история не перезаписывается, а дополняется событиями;
- секреты в таблицах не хранятся.

## Сущности

### `users` — пользователи

Один известный пользователь внутри экземпляра компании.

Основные данные:

- внутренний идентификатор;
- дата первого и последнего обращения;
- подтверждённые контактные данные;
- общий контакт, если идентификаторы разных каналов удалось связать;
- дата создания и обновления.

### `channel_identities` — идентификаторы каналов

Связывает пользователя с Telegram, Авито, сайтом, VK, MAX или другим источником.

Основные данные:

- пользователь;
- код канала;
- внешний идентификатор пользователя;
- внешний идентификатор чата;
- дата первого и последнего сообщения;
- возможность отправлять отложенные сообщения.

Уникальность канала и внешнего идентификатора защищает от повторного создания пользователя.

### `conversations` — диалоги

Отдельный разговор пользователя с ботом.

Основные данные:

- пользователь;
- канал;
- время начала и окончания;
- текущий этап;
- текущий статус;
- итоговый результат;
- время последнего сообщения пользователя;
- время последнего ответа бота;
- версия workflow и prompt;
- признак передачи человеку.

### `messages` — сообщения

Каждое входящее и исходящее сообщение.

Основные данные:

- диалог;
- направление: входящее или исходящее;
- автор: пользователь, бот или менеджер;
- исходный текст;
- обезличенный текст;
- внешний идентификатор сообщения;
- время получения или отправки;
- статус доставки;
- связь с сообщением, на которое дан ответ;
- идентификатор выполнения n8n.

Исходный текст имеет более строгий доступ и отдельный срок хранения.

### `stage_events` — история этапов

Каждый переход между этапами.

Основные данные:

- диалог;
- предыдущий и новый этап;
- время перехода;
- причина;
- источник решения: правило, LLM или человек;
- уверенность модели.

### `goal_events` — целевые события

Фиксирует достигнутые результаты:

- получен телефон;
- явное намерение заказать;
- запись на замер;
- будущие цели компании.

Основные данные:

- пользователь и диалог;
- код цели;
- время;
- источник подтверждения;
- доказательный фрагмент;
- уверенность;
- подтверждение человеком.

### `followups` — напоминания

Планирует и фиксирует отложенные сообщения.

Основные данные:

- диалог;
- номер напоминания;
- запланированное время;
- статус;
- время отправки;
- результат доставки;
- причина отмены;
- число попыток.

### `conversation_analysis` — анализ диалога

Результат отдельной оценки качества.

Основные данные:

- краткое резюме;
- тема и намерение;
- реакция пользователя;
- возможные ошибки;
- вопросы без ответа;
- пробелы базы знаний;
- причина потери;
- уверенность;
- модель, prompt и версия анализа;
- подтверждение человеком.

### `feedback` — обратная связь

Явная оценка пользователя.

Основные данные:

- диалог;
- оценка;
- текст;
- время;
- канал.

### `integration_events` — внешние интеграции

Попытки работы с CRM и каналами.

Основные данные:

- компонент;
- операция;
- внешний идентификатор;
- статус;
- число попыток;
- краткая ошибка;
- время начала и завершения.

### `system_events` — технические события

Сбои и предупреждения.

Основные данные:

- workflow;
- идентификатор выполнения;
- компонент;
- уровень важности;
- тип события;
- безопасное описание;
- время;
- статус обработки уведомления.

### `knowledge_documents` — документы базы знаний

Оригиналы и версии загруженных документов.

Основные данные:

- название;
- компания или schema назначения;
- исходный файл;
- контрольная сумма;
- версия;
- статус обработки;
- дата загрузки;
- разрешённый Telegram user ID;
- сведения об ошибке;
- дата публикации и архивирования.

### `knowledge_chunks` — чанки

Подготовленные части документа для поиска.

Основные данные:

- документ и версия;
- порядковый номер;
- очищенный текст;
- заголовок и раздел;
- метаданные источника;
- вектор;
- модель embeddings;
- размер;
- статус публикации.

### `dashboard_settings` — оформление дашборда

Безопасные настройки интерфейса:

- название компании;
- путь к логотипу;
- цвета;
- часовой пояс;
- порядок этапов;
- видимые разделы;
- период по умолчанию.

Эта таблица не управляет логикой бота.

## Данные, которые не хранятся здесь

- API-токены;
- пароли;
- n8n Credentials;
- административный ключ Supabase;
- секреты CRM;
- полный системный prompt, если он содержит закрытые данные.

## Следующий шаг

Перед SQL нужно утвердить:

- точные названия таблиц и полей;
- связи и обязательность полей;
- сроки хранения исходного текста;
- права доступа;
- индексы;
- правила удаления и обезличивания;
- представления для дашборда.
