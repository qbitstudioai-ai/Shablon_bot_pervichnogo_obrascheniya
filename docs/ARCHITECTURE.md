# Архитектура проекта

Статус: базовая архитектура согласована. SQL, индексы и workflow ещё не созданы.

## 1. Состав одной установки

Каждая компания получает независимый комплект:

1. клиентский бот;
2. отдельный служебный Telegram-бот;
3. два независимых workflow n8n;
4. отдельную schema Supabase;
5. настройки компании и дашборда;
6. собственные Credentials и токены.

Клиентский workflow ведёт диалог. Служебный workflow принимает документы базы знаний и отправляет технические уведомления. Это два разных назначения, поэтому служебный workflow не считается частью клиентского диалога.

## 2. Поток клиентского сообщения

1. Сообщение приходит из Telegram, сайта, Avito, VK, MAX или другого канала.
2. n8n определяет компанию и канал по конкретному workflow и его настройкам.
3. Сообщение сохраняется в schema этой компании.
4. n8n загружает состояние диалога и при необходимости ищет информацию только в базе знаний этой компании.
5. Модель формирует ответ.
6. Ответ отправляется пользователю и сохраняется в Supabase.
7. Обновляются этап, целевые события, напоминания и данные для аналитики.

Workflow не должен принимать название schema из сообщения пользователя. Schema задаётся при внедрении и считается технической настройкой.

## 3. Изоляция компаний

Для каждой компании используется отдельная schema, например:

- **kompaniya_001**
- **kompaniya_002**

Внутри schema находятся и рабочие данные, и база знаний компании. Клиентский и служебный workflow жёстко привязаны к одной schema. Они не выбирают компанию во время работы.

Обязательные меры:

- отдельные токены Telegram и Credentials n8n;
- минимальные права доступа для каждого компонента;
- service role Supabase хранится только на серверной стороне;
- дашборд не получает service role;
- поиск по базе знаний выполняется функцией, которая работает только с разрешённой schema;
- тесты должны проверять не только разрешённый доступ, но и запрет доступа к чужой schema.

## 4. Служебный Telegram-бот

У каждой компании свой служебный бот и свой токен. Через него разрешённые сотрудники:

- загружают Markdown-документы;
- получают результат обработки;
- получают уведомления об ошибках n8n, Supabase, каналов и поиска;
- в дальнейшем могут запрашивать состояние системы.

Служебный workflow заранее знает компанию. Пользователь не выбирает компанию командой и не передаёт schema в имени файла.

## 5. Загрузка базы знаний

Путь документа:

1. Telegram принимает файл.
2. n8n проверяет отправителя, расширение и размер.
3. Файл скачивается, проверяется и получает SHA-256.
4. Markdown разбирается, очищается и делится по смысловой структуре.
5. Для фрагментов создаются embeddings.
6. Новая версия сохраняется как неактивная.
7. Выполняются автоматические проверки и контрольный поиск.
8. Новая версия становится активной.
9. Предыдущая версия архивируется.
10. Служебный бот отправляет отчёт.

Подробные требования: [KNOWLEDGE_INGESTION.md](specs/KNOWLEDGE_INGESTION.md).

## 6. Хранилища Supabase

В schema компании находятся группы таблиц:

- пользователи и идентификаторы каналов;
- диалоги и сообщения;
- этапы, целевые события и напоминания;
- анализ диалогов и обратная связь;
- документы и фрагменты базы знаний;
- системные события;
- настройки дашборда.

Векторное расширение pgvector хранит embedding каждого фрагмента. Для сравнения всех активных фрагментов используется одна и та же модель embedding с одинаковой размерностью.

## 7. Дашборд

Дашборд руководителя показывает:

- обращения и уникальных пользователей;
- конверсию в телефон, запись на замер и явное намерение заказать;
- долю потерянных пользователей;
- этапы, на которых прекращаются диалоги;
- переписки и историю смены этапов;
- ошибки и проблемы ответов;
- реакцию и обратную связь клиентов;
- состояние интеграций.

Админ-панель разработчика управляет логотипом, названием компании, каналами, разрешёнными служебными пользователями, настройками напоминаний и другими параметрами внедрения. Секретные токены в браузере не показываются и не редактируются открытым текстом.

## 8. Надёжность

- Входящие события должны иметь внешний уникальный идентификатор, чтобы повторная доставка не создавала дубль.
- Любая ошибка записывается в **sistemnye_sobytiya**.
- Неуспешная загрузка документа не отключает старую базу знаний.
- Напоминания через 20 минут и через 24 часа выполняются отдельным плановым процессом.
- После второго напоминания и отсутствия ответа пользователь считается потерянным.
