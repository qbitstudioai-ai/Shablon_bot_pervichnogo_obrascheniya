# Архитектура шаблона

Нормативная основа v0.3. Это описание будущей системы; исполняемых компонентов пока нет.

## Общая инфраструктура и экземпляры компаний

Базовое размещение — один российский сервер с отдельными сервисами n8n, Supabase/PostgreSQL/pgvector, локальной псевдонимизации и серверных частей дашбордов. Внешние LLM и embedding API получают только разрешённые подготовленные данные и остаются заменяемыми адаптерами. Точные границы и обязательные проверки: [INFRASTRUCTURE_RU_SERVER](INFRASTRUCTURE_RU_SERVER.md).

Одна серверная установка Supabase содержит одну рабочую базу PostgreSQL с pgvector. Разделение компаний — по schema одинаковой структуры. Studio используется Павлом для управления; клиентам доступ к Studio не предоставляется.

Одна установка n8n исполняет копии шаблонов разных компаний. Общая инфраструктура требует защиты доступа и контроля нагрузки. Отдельная schema не равна физически отдельной БД. Точные права определяет [ACCESS_AND_ISOLATION.md](specs/ACCESS_AND_ISOLATION.md).

Для компании создаются два основных workflow:

1. **Компания — Бот первичного обращения**: клиентские каналы, общая логика, интеграции и запуск проверки напоминаний по расписанию.
2. **Компания — Служебный бот и база знаний**: собственный Telegram Trigger, загрузка Markdown, отчёты и отправка системных уведомлений Павлу.

Если обработка ошибок требует отдельного Error Workflow, это технический обработчик шаблона без второго Telegram Trigger для того же токена. Отправлять уведомления одним токеном могут несколько доверенных процессов; получать входящие обновления — один активный webhook на токен. Тестовые боты имеют другие токены, чем рабочие.

Дашборд каждой компании разворачивается отдельно вместе с серверным API. Это не общий клиентский интерфейс для переключения между компаниями.

## Сквозная схема

~~~mermaid
flowchart TD
    A["Клиентские каналы"] --> B["Адаптеры и клиентский workflow"]
    B --> C["Schema компании: данные, очередь, память"]
    C --> B
    B --> D["LLM и выбранная CRM"]
    B --> A
    E["Служебный Telegram-бот компании"] --> F["Служебный workflow"]
    F --> C
    F --> E
    B --> F
    G["Дашборд и его серверный API"] --> C
~~~

На схеме Supabase один. C означает разрешённую schema, а не отдельный облачный проект.

## Неизменяемое ядро и адаптеры

Каналы Telegram, сайт, Авито, VK, MAX — адаптеры одного продукта. Их поддержка в архитектуре не означает готовую интеграцию: каждый адаптер допускается к запуску после проверки своего API.

Входной адаптер проверяет источник запроса и приводит событие к общему формату. Ядро не зависит от названий полей Telegram или Авито. Ответ всегда возвращается в исходный канал и исходный диалог. LLM не выбирает адресата, токен, компанию или schema.

В клиентском workflow визуально выделяются:

| Блок | Содержание | При обычном внедрении |
|---|---|---|
| МЕНЯТЬ ПРИ ВНЕДРЕНИИ | Компания, schema, часовой пояс бизнеса, модели, prompts, выбранные каналы/CRM, параметры и ссылки на Credentials | Заполняется по паспорту |
| CORE — НЕ ТРОГАТЬ | Нормализация, защита от дублей, очередь, обезличивание, память, поиск, проверка ответа, цели, напоминания, ошибки | Не редактируется |
| АДАПТЕРЫ | Вход/выход каналов, выбранная CRM, уведомления | Подключаются нужные |

Поведение бота настраивается в n8n. Supabase хранит данные и состояние выполнения. Сохранение срока напоминания в БД — состояние задачи, а не альтернативная панель управления логикой. Админ-панель v1 меняет только разрешённые параметры интерфейса.

CRM выбирается явно: **net**, **bitrix24** или **amocrm**. Работает одна выбранная ветка. Режим без CRM имеет подтверждаемую локальную заявку; неподключённые интеграции не вызываются.

## Обработка обращения

1. Проверить подлинность источника, определить экземпляр из серверных настроек.
2. Надёжно зарегистрировать входящее событие и исходное сообщение до вызова LLM.
3. Последовательно обработать сообщения конкретного диалога.
4. Получить короткую рабочую память; не загружать весь архив.
5. Удалить из контекста лишние персональные данные; найти разрешённые активные знания.
6. Получить ответ и предложенное действие LLM, проверить их правилами.
7. Сохранить исходящее действие до обращения к внешнему API.
8. Отправить ответ и отдельно записать подтверждение канала.
9. Применить допустимый переход состояния, обновить память и задачи.
10. Выполнить CRM и аналитические действия с отдельным учётом результата.

Транзакция БД не может атомарно охватить Telegram или CRM. Правила частичных сбоев: [RELIABILITY_AND_MEMORY.md](specs/RELIABILITY_AND_MEMORY.md). Форматы обмена: [INTEGRATION_CONTRACTS.md](specs/INTEGRATION_CONTRACTS.md).

Фраза «Ваша заявка принята, с вами свяжется специалист» допустима после надёжной регистрации заявки и согласованного маршрута передачи. Она закрывает автоматическое ожидание ответа. Телефон как целевое событие сам по себе разговор не завершает. Все сроки и условия — только в [CONVERSATION_LIFECYCLE.md](specs/CONVERSATION_LIFECYCLE.md).

## Знания, аналитика и управление

Markdown проходит проверку, структурную очистку, деление и проверочную индексацию. Новая версия публикуется одним переключением после проверки; старая остаётся рабочей при ошибке. Детали: [загрузка знаний](specs/KNOWLEDGE_INGESTION.md).

Исходные сообщения и доказательства целей сохраняются отдельно от предположений модели. Дашборд считает показатели по [METRICS.md](specs/METRICS.md). Права Павла и руководителя определены в [DASHBOARD_ADMIN.md](specs/DASHBOARD_ADMIN.md).

GitHub хранит эталон и историю изменений. Для каждой рабочей копии известны версия шаблона, применённые изменения БД, версия конфигурации и результаты приёмки. Обновление ядра сначала проверяется на тестовой копии; перенос не затирает настройки компании.
