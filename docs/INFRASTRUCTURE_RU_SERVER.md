# Размещение продукта на российском сервере

Статус: базовая архитектурная позиция для будущей реализации. Документ не подтверждает, что сервер уже подготовлен, а сервисы установлены или испытаны.

## Принятое решение

Основные компоненты шаблона размещаются на одном российском сервере:

- n8n как оркестратор процессов;
- одна self-hosted установка Supabase/PostgreSQL;
- pgvector внутри PostgreSQL;
- локальный модуль очистки и псевдонимизации данных;
- серверные части и веб-интерфейсы дашбордов;
- reverse proxy, технические журналы и мониторинг в утверждённых границах.

Один физический сервер не означает один процесс. Компоненты разворачиваются как отдельные сервисы или контейнеры с разными доступами и лимитами. Это позволяет позже вынести тяжёлый сервис на другой российский сервер без изменения бизнес-логики.

## Важная граница российского контура

Базовый вариант допускает внешние API:

- DeepSeek или совместимый провайдер — диалог, классификация и подготовка ответа;
- Qwen Embedding API или совместимый провайдер — создание векторов для поиска знаний.

Поэтому схема является **российским размещением основной инфраструктуры**, но не полностью закрытым контуром обработки. Во внешний API передаётся только минимально необходимый подготовленный пакет. До отправки локально удаляются или заменяются персональные данные и запрещённые сведения.

Если договор, закон или политика компании запрещают передачу подготовленного текста внешнему провайдеру, внешний адаптер не используется: LLM и/или embedding-модель должны быть заменены локальным сервисом. Такая замена не должна менять CORE, структуру данных и правила продукта.

## Движение данных бота

~~~mermaid
flowchart TD
    A["Канал клиента"] --> B["n8n на российском сервере"]
    B --> C["Supabase: событие и состояние"]
    B --> D["Локальная псевдонимизация"]
    D --> E["Внешний AI API: обезличенный пакет"]
    E --> B
    B --> C
    B --> A
    C --> F["Сервер дашборда компании"]
~~~

Перед внешним вызовом входное сообщение уже надёжно зарегистрировано. Внешняя модель не получает токены каналов, имя schema, SQL, адресата, права доступа или исходные персональные поля и не может сама отправить сообщение клиенту. Её ответ считается предложением: CORE проверяет структуру и допустимое действие.

Если в подготовленном тексте использованы метки `PERSON_01`, `PHONE_01` и подобные, таблица соответствий остаётся только в российском Supabase. Обратная подстановка допускается локальным контролируемым модулем только там, где она действительно нужна; LLM не получает таблицу соответствий.

## RAG и embeddings

Supabase хранит оригинал разрешённого документа, версии, фрагменты, состояние публикации и вектора. Embedding API не является хранилищем.

Текст каждого фрагмента, отправленного во внешний embedding API, покидает российский сервер. Поэтому:

- открытые и разрешённые технические знания можно отправлять после очистки;
- персональные данные удаляются или заменяются до отправки;
- конфиденциальные сведения отправляются только при явном разрешении политики внедрения;
- при запрете внешней передачи используется локальная embedding-модель;
- бот ищет только в опубликованной версии знаний своей компании.

## Изоляция компаний

Одна установка Supabase обслуживает несколько компаний, но разделение является обязательным правилом, а не рекомендацией:

- у каждой компании и среды отдельная schema одинаковой структуры;
- у n8n и серверной части дашборда отдельные ограниченные роли;
- общий `postgres`, `service_role` и административные ключи не используются в обычной работе;
- schema не выбирается из сообщения клиента, ответа LLM или параметра браузера;
- Credentials, токены, рабочие процессы, настройки и дашборд компании отделены;
- test и production не используют одни токены, входы и роли;
- отрицательные проверки должны доказать, что компания A не читает и не меняет данные компании B.

Подробные правила доступа остаются в [ACCESS_AND_ISOLATION](specs/ACCESS_AND_ISOLATION.md).

## Что и где хранится

| Данные | Постоянное место | Во внешний AI API |
|---|---|---|
| Исходные сообщения и контакты | Schema компании в Supabase | Нет в исходном виде |
| Таблица соответствия псевдонимов | Защищённая область российской БД | Никогда |
| Состояние диалога, задачи и подтверждения | Supabase | Только необходимый обезличенный контекст |
| Документы знаний и версии | Supabase компании | Только разрешённые очищенные фрагменты |
| Embeddings | pgvector в Supabase | API возвращает вектор; не хранит состояние продукта |
| Секреты каналов и интеграций | Credentials/серверные секреты | Никогда |
| Метрики и журнал действий | Supabase | Только если это отдельно требуется и разрешено |

n8n не является основной БД, хранилищем документов, секретов или единственной памятью диалога. Значимое состояние сохраняется в Supabase до следующего внешнего действия.

## Заменяемые адаптеры

CORE обращается не к названию конкретного провайдера, а к согласованному интерфейсу:

- `LLM adapter`: DeepSeek, другая внешняя LLM или локальная модель;
- `Embedding adapter`: Qwen, другой API или локальная модель;
- адаптеры каналов и CRM;
- серверный API дашборда.

Смена провайдера требует испытаний качества, форматов, лимитов, стоимости и политики данных, но не переписывания жизненного цикла бота.

## Что необходимо проверить до реализации

- ресурсы и запас мощности сервера для одновременной работы Supabase, n8n и дашбордов;
- резервное копирование и проверенное восстановление;
- шифрование соединений, закрытие PostgreSQL/Studio от публичного доступа и правила исходящего трафика;
- перечень данных, разрешённых каждому внешнему провайдеру;
- сроки хранения сообщений, журналов и временных файлов;
- лимиты n8n, очистку execution data, мониторинг очередей и свободного места;
- отдельные test/production-доступы и безопасный выпуск;
- возможность заменить внешние AI API без потери истории и изменения CORE.

До этих проверок схема считается архитектурным решением, а не доказанной production-готовностью.
